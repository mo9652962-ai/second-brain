# SOP-001: 复杂多步故障排查与根因修复标准流程

- **ID**: SOP-001
- **Category**: OPS（运维/排障）
- **状态**: Active
- **维护者**: k

## 1. 前置条件与触发上下文

- **触发**: 复杂系统报错 / 多步任务失败 / 需要根因分析而非表面修复
- **前置**: 能访问报错日志 / 可复现环境 / 记录工具（Hermes terminal/read_file）
- **反模式**: 盲目猜测 → 乱试 → 越修越坏（禁止）

## 2. 确定性执行步骤

```
① 捕获完整报错堆栈 + 最小可复现用例
   - 完整错误信息（不截断）
   - 能稳定复现的最小命令/输入
② 隔离变量，构造前置 Smoke Test
   - 逐个变量排除（配置/依赖/网络/权限/版本）
   - 先测最小路径（如版本确认 → 依赖存在 → 权限）
③ 执行修复
   - 每次只改一个变量
   - 改完立即验证（不是改完一起验证）
④ 回归测试
   - 原问题复现路径重跑
   - 相关功能冒烟（确认没修出新问题）
⑤ 提炼根因 + 规避准则入库
   - 根因一句话说清（不是症状）
   - 更新对应技能/SOP 的 Gotchas 节
```

## 3. 验证与验收边界

```
✅ 原报错不再出现（复现路径重跑通过）
✅ 最小用例通过
✅ 相关功能无回归
✅ 根因已记录（后续会话可查到）
❌ 未达标准: 「看起来好了但不知道为什么」= 不算完成
```

## 4. 异常恢复与常见陷阱

```
⚠️ 陷阱: 网络错误可能是代理问题（先测 curl 代理本身 200 再查别的）
⚠️ 陷阱: 版本号显示旧版 = 命令路径指向错误安装（which 确认）
⚠️ 陷阱: 时间戳异常报错（npm ETARGET before 时间 = 客户端 bug 不是 registry）
⚠️ 陷阱: 多个进程自动重启（taskkill 后服务又拉起 = 查服务/守护进程）
⚠️ 修复: 复杂依赖树被破坏 → 优先「重装/补齐」而非手动改文件
```

## 二、方案核心（EVAL_PLAN.md）

### 三臂设计（比二臂更科学）

| 臂 | 配置 | 回答的问题 |
|:---|:---|:---|
| S | 单 Agent + 标准 gate | 基线 |
| M | 多 Agent + 标准 gate | 多 agent 是否提升质量/安全 |
| NG | 多 Agent **去 gate** | **gate 是否真的有用**（关键增量）|

- 180 run = 60 匹配任务 × 3 臂（10 开放 + 10 原有，各扩 3 实例）
- 任务 ID 作配对键 → 可用 McNemar（不能把任务难度差异误当成架构差异）
- 原 20 题保留为 Regression-20（低成本回归集）

### 10 个开放任务（task_cards.jsonl）

T01 版本冲突政策 / T02 间歇故障 RCA / T03 遗留 API 迁移 / T04 Agent 安全威胁建模 / T05 截止日期研究综述 / T06 脏数据分类清洗 / T07 工具供应商决策 / T08 需求冲突到 PRD / T09 知识库冲突与投毒 / T10 长时可恢复协作

→ T04/T09/T10 直接映射我们真实场景（安全边界/知识库治理/429 恢复）

### grader 健壮性（fail-closed 核心）

- 确定性硬门 **优先于** LLM judge，judge 不能覆盖硬门失败
- judge 严格 JSON：label/dimensions/evidence_spans/confidence/unknown_reason，多余字段拒绝
- 失败分级：pass / fail / review / grader_error / infra_error（环境失败与 agent 质量分开）
- Golden/负例规范：8 正常 + 4 语义变体 + 4 boundary + 4 adversarial，mutation testing

### 失败归因十分类（failure_attribution.py）

INFRA / TIMEOUT / TOOL / ORCH / BUDGET / GATE / PARSE / TASK / DATA / UNKNOWN
主因 = 最早未恢复阻塞点（429 恢复后不算主因；输出对但解析器崩 = PARSE 不是 TASK）

```
无门+judge unknown → REVIEW ✅
judge 多余字段 → GRADER_ERROR ✅ 严格拒绝

```

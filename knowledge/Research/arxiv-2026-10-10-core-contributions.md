## 🥇 One Skill Too Many: How Co-Installed Skills Conflict in Coding Agents (2610.11647)

**标题**: One Skill Too Many: How Co-Installed Skills Conflict in Coding Agents
**作者**: Chaoliang Yan, Zihao Xu, Yuekang Li, Shangzhi Xu, Yi Liu, Gelei Deng, Siqi Ma（UNSW 等四校）
**分类**: cs.SE, cs.AI ｜ 投稿状态：arXiv preprint v1（2026-10-08）
**核心**: 技能来自独立来源（团队 / 开发者 / 插件 / 拷贝合集），一个已装技能可能与**做同一件事**的相似技能共装，而模型**仅凭名称与描述**二选一。冲突时已装技能丢掉核心功能（例如「禁止碰 git」被绕过），**而任务仍然通过**——所以只看任务完成度的基准测不出。首个实证研究。

### 核心贡献表

| 发现 | 数据 | 对 k 的意义 |
|:---|:---|:---|
| **共装冲突是常态** | 20,947 个仓库快照 → 822,109 个疑似相似技能对 → LLM 判定 3,754 个分层样本 → 312 个确认对进实验 | 这不是边缘情况，是技能生态的结构性特征 |
| **近 1/4 已装技能有同功能共存者** | 同一安装列表内 23.5%（95% CI 21.2%–25.7%），约 10,100 个「家族」；若算上「用户可再加的同功能技能」达 63.7% | k 本地 459 个 SKILL.md，同名重复 2 组、Jaccard≥0.5 近似对 5 组（10-10 实测）——量级一致 |
| **任务通过 ≠ 技能生效** | 相似技能在**不降低任务完成率**的前提下抢走 **1/5 运行**；先打开相似技能的运行丢掉 **>1/3** 独占核心功能（37% vs 共享功能 8%） | 必须专测**独占核心功能**（「不许碰 git」「发布前必过隐私门禁」），完成率测不出来 |
| **位置决定谁跑** | **安装位置**决定（个人目录 vs 插件），列表顺序几乎无关；B 放个人目录 → A 从全部 243 个列表消失、A 使用率 −35.0pp、46.5% 运行改用 B | 装技能的位置就是优先级策略，不是排序 |
| **回复不告诉你谁干的** | 113 次替换运行里，最终回复**只在 0.9%** 点名实际使用的技能；全部 A+B 运行里 7.7% 提到技能名 | 「点名本次生效的技能」是 0.9% → 高覆盖的巨大低成本缺口 |
| **冲突在「首次读技能」定案** | 97% 的 B-first 运行在打开 B 之前**未改动任何文件**；该处加 PreToolUse hook（拒绝首次读 B、点名让模型用 A）→ 模型 **96%** 切回 A，独占核心功能保真度 **+9.1pp**（双方都先够 B 的场景 +17.8pp），重定向运行与「先打开 A」持平（0.0pp），**任务完成率不变** | 干预点极便宜：一个文件读，在任何改动之前；代价是必须**声明哪个是 A** |

### 方法/架构

```
20,947 个仓库快照（公开 SKILL.md，2026-07-18 采集）
    ↓ 按 Claude Code 加载规则还原 5,106 个「安装列表」
    ↓ 名称+描述嵌入 → 每技能取 10 近邻 → 822,109 个候选对
    ├─ 跨项目 439,860 / 项目内 382,249
    ↓ LLM judge 3,754 个分层样本 → 确认 1,639 个「同一件事」→ 312 个可跑可评分对
    ↓ 3 模型 × 312 对（6,368 运行 / 169,294 工具调用 / 542 agent 小时）
    ├─ 抽取「核心功能」：称职模型通常不会自发改的、可核查的要求（禁令也算）
    │     └─ 标注 exclusive（仅 A 要求，73% of 2,518）vs shared
    ├─ 对照组：A only / A+B / A+C（无关技能）
    └─ 干预：PreToolUse hook 守「首次技能读取」
```

| 指标 | A+B vs A only |
|:---|:---|
| 用到 A 的运行 | **−19.9 pp** |
| 任务完成率 | +1.9 pp（CI 跨零，不显著） |
| A 的核心功能保真度（前三条） | −2.6 pp |
| **A 的独占核心功能** | **−5.6 pp** |
| A 的共享核心功能 | +0.1 pp（无变化） |
| 对照：加无关技能 C | A 使用率仅 −5.9 pp，保真度无变化 |

> 关键对照：**问题不是「多了一个技能」，而是「多了一个干同一件事的技能」**。失效形态以**整体替换**为主（12.1% 只用 B、38.0% 两个都不用），而非混合。

### 与 sora 的关联

- 🔴 **直接命中 k 自己的技能库**：Hermes 活跃技能 459 个（10-10 本地实测，已排除 `.archive`），同名重复 2 组（`ai-image-generation` @okaris 版 vs 自建版、`manim-video` creative/ vs video-use/）——**同名 = 触发条件完全重叠，只有加载顺序能决定谁跑**，是最高优先级冲突源
- ✅ **方法论修正**：skill-audit 现在只看 description 是否过时，**没有独占功能断言**——本文给出的「专测独占核心功能」正是缺的那一环
- ✅ **技能生命周期三环闭环**：10-02 卡片「装的时候危险」（技能即供应链）→ 10-04 卡片「执行的时候危险」（批准的动作 ≠ 执行的动作）→ 本篇「共存的时候危险」（抢跑且不报名字）
- ⚠️ **对「全都要」原则的精确边界修正**：sora 的偏好是搜索/模型/技能一次配多个冗余。冗余在**模型侧是容灾**，在**技能侧是冲突**——同一件事两个技能，谁跑由安装位置决定，而输出不会告诉你

## 🥈 Do Tool Calls Execute as Intended? Measuring and Repairing Intent-Execution Correspondence in LLM Agents (2610.04375)

**标题**: Do Tool Calls Execute as Intended? Measuring and Repairing Intent-Execution Correspondence in LLM Agents
**作者**: Boyang Yang, Zhenhao Li, Ziyao Yang, Kanghui Jia, Xin Yin, Mingmou Liu, Haoye Tian（燕山大学、Aalto 大学等）
**分类**: cs.AI, cs.SE ｜ 投稿状态：arXiv preprint v1（2026-10-03）
**核心**: 一个工具调用要经**多个跳（hop）**才到达程序，任一跳都可能**无声改动**它。改动后的调用失败时，agent 会重试一个**正确的**调用，白烧用户的时间与钱。基准与失败分析看不见这个改动——因为它们读的是「调用及其结果」，而不是「**某一跳收到了什么**」。作者定义 **intent-execution correspondence（IEC）**：执行的动作与发出的调用在工具契约下所指的动作一致。

### 核心贡献表

| 发现 | 数据 | 对 k 的意义 |
|:---|:---|:---|
| **改动率高且集中** | 生产会话 **47,828 次 shell 调用**中，Claude Code 的 Bash 工具改动了 **12.0%** 携带代码/转义序列/长文本的调用（902 / 7,491） | k 每天跑的正是这类调用（含引号、`&&`、反斜杠、MSYS 路径） |
| **静默执行错误动作** | 反斜杠被改动的调用中 **80.7%**（535 / 663）在**没有任何报错**的情况下执行了错误动作 | 「没报错」不等于「跑对了」——这是最贵的失效形态 |
| **全部 harness 都改** | 被测 **10 个 harness 全部**会改动调用 | 不是某个工具的 bug，是架构层性质 |
| **归因被系统性带偏** | 基于轨迹的判断把 **95.1%** 的生产失败归因给 LLM，尽管**超过一半**是执行路径造成的 | k 排障时「调用失败 → 怀疑模型/工具」的默认路径是错的 |
| **成本可量化** | IEC-Bench 上路径把**每通过任务的 token 成本抬高 2.4×**（最高 **12.3×**） | 失败重试的成本会藏在 token 账单里 |
| **改动会遮蔽后续改动** | 改动的跳同时**遮蔽其后所有改动** → 某路径 **55.1%** 的失败要等第一跳被修复后才显现 | 修一层才暴露下一层，别指望一次定位 |
| **修复有效** | **IntAct**（以该跳无法改动的方式投递调用，或直接拒绝）已在商业产品部署，恢复 **79.2%** 的改动调用失败（137 / 173） | 「投递形式不可改」+「拒绝」是可落地的两个动作 |

### 方法/架构

```
agent 发出的调用
    ↓ hop 1（harness 工具层，如 Bash tool）
    ↓ hop 2（shell 包装 / 路径转换 / 编码层）
    ↓ hop 3（接收方解析器）
    └─ 任一跳可无声改动 → 执行的动作 ≠ 发出的调用所指的动作（IEC 破坏）

测量协议：不执行调用，逐跳观测「这一跳收到了什么」
         用接收方自己的解析器指认第一个改动它的跳
修复 IntAct：a) 以该跳无法改动的方式投递  b) 拒绝该调用
```

### 环境细节（对 k 尤其重要）

- 生产语料来自**一家公司六名开发者、11 周、Windows 上的 Git Bash + PowerShell 5.1**
- 同论文报告：在 **Linux** 上把命令作为参数交给 `bash -c`，约 **167,000 次调用中零改动** —— 即**改动是 Windows 路径/引号/转义链路特有的**，不是普遍现象
- ⚠️ 作者建议：**逐跳测试 harness**——「确保正确的调用按意图执行，或被拒绝」

### 与 sora 的关联

- 🔴 **k 的运行环境就是论文的高危环境**：本机 `terminal` 走 git-bash（MSYS），且系统提示已明确「MSYS 路径转换被禁用」——`git -C /c/Users/<user>`、`node /tmp/a.js` 会失败而 `cd /c/Users/<user>` 可以。这正是本文描述的「hop 改动了调用」
- 🔴 **k 已记录过同类失效**：记忆里的「垃圾文件名（含引号/&&）Windows 无法落盘、status 假象 → 用 `git ls-tree` 验证」就是 IEC 破坏的一个实例——当年是靠结果对账发现的，本文给了机制解释与前置观测方法
- ✅ **三条可立即落地的排障规则**：① shell 调用（尤其含引号/转义/长文本）失败时**先验「实际执行的是什么」**，别先改命令；② 失败归因不要只看轨迹（95.1% 被误归因）；③ 观测每一跳「收到了什么」，而非只看结果
- ✅ **与既有坑清单合流**：写码前扫坑 32 项 / `windows-file-lock-troubleshooting` / `windows-node-deployment` 三条技能可增补「IEC 自检」步骤

## 🥉 What to Admit and How to Present: Governing Persistent Memory in LLM Agents (2610.11188)

**标题**: What to Admit and How to Present: Governing Persistent Memory in LLM Agents
**作者**: Chang Liu, Deliang Ding
**分类**: cs.AI ｜ 投稿状态：arXiv preprint v1（2026-10-05 前后）
**核心**: 持久记忆能提升个性化，但也会诱发**谄媚与跨域泄漏**。作者把治理拆成两个可分离的决策：**admission（什么召回信息进入工作上下文）** 与 **presentation（已准入信息如何表达）**。实现两个免重训的推理时设计：FC（整条评估）与 PS（把条目分解为带类型的单元，映射到六类许可：五种可用 + deny）。

### 核心贡献表

| 发现 | 数据 | 对 k 的意义 |
|:---|:---|:---|
| **只有 admission 显著有效** | 相对逐字注入，FC / PS 把外部基准合并 judge 失败率降低 **6.7 / 8.8 pp**（p = 2.7e-7 / 4.1e-12）；开发集跨域泄漏最多降 **29.5 pp** | 力气该花在**筛选**，不是改写措辞 |
| **presentation 无显著差异（反直觉）** | 固定准入、比较**同一裁定输出的两种渲染**（PN vs CH）→ **九个任务-指标对里没有一项**通过多重比较校正 | k 常花力气润色记忆/提示的措辞——本文实测这一轴**几乎不产生安全收益** |
| **收紧准入再降跨域失败** | 固定 presentation、收紧 admission → 跨域失败再降 **17.5 pp**（p = 1.6e-4） | 准入是**可连续加力的杠杆**，与表达解耦 |
| **单 bit 准入不够** | 查询条件化 gating 基线（MemGate 复现）在客观事实失败与合并失败上**无显著变化** | 「按相关性保留/丢弃」这种单 bit 准入是粗糙的，需要裁定属性 |
| **代价是真实的** | 两个设计**都增加个性化失败**；PS **未达到**预注册的改进与个性化保留标准；记忆-证据冲突下误导率仍 82.3–85.0%（Bare 91.7%） | 安全与个性化存在权衡，**别宣称两全**——诚实报告副作用是本文的加分项 |
| **PS 优于随机/相关性选择** | 匹配准入预算下，PS 在 Holm 校正后仍优于随机与相关性选择（外部客观事实判断） | 单元级分解（把「我偏好 A 因为续航久」拆成偏好单元 + 事实声明单元）确实带来选择优势 |

### 方法/架构

```
生成时：检索 top-k 记忆 M = {m1..mk}（查询 q）
    ↓ 治理 = 两个映射的复合
    ├─ Admission A：m → 类型化单元 U(m)（FC 判整条；PS 先拆单元）
    │     └─ 批量裁定调用一次看到 query + answer target + task mode + 全部 top-k
    │           （支持跨记忆冲突检测）→ 只赋「属性」，不赋「动作决策」
    │     └─ 确定性代码把属性编译成 6 类许可（5 可用 + deny）；deny 单元物理移出
    └─ Presentation P：决定已准入单元的表面形式
          └─ PN（许可说明分节）vs CH（信息类型通道分节）
    ↓ 两个杠杆都只在推理时生效：不重训、不删除、不改存储内容
```

| 任务 | Bare | Gate | FC | PS |
|:---|:---|:---|:---|:---|
| ofj 客观事实判断 | 45.2 | 45.5 (p=1.0) | 23.7 | **20.4** |
| csc 上下文范围控制 | 33.3 | 22.7 | 27.0 | 25.3 |
| mec 记忆-证据冲突 | 91.7 | 85.7 | 85.0 | 84.0 |
| pm 个性化记忆使用（越低越好） | 14.7 | 22.7 † | 22.3 † | 20.0 † |
| **合并（n=1,199）** | 46.2 | 44.1 (p=.08) | **39.5** | **37.4** |

> † = 相对 Bare 失败率**上升**。准入收紧换来安全，代价是个性化能力下降。

### 与 sora 的关联

- 🔴 **k 的记忆治理直接受益**：现在的做法是「读取 → 直接用」，缺少显式的准入裁定层。可落地：**记忆读取先做准入裁定（这条该不该进上下文），别急着润色**
- ✅ **纠正一个直觉错误**：k 在整理 MEMORY.md / 记忆条目时习惯反复改措辞——本文说这一轴**不产生可测安全收益**，该把力气移到「准入与分型」
- ✅ **与记忆分型研究合流**：2610.11573（Memory Type Varies，TriMEM 分型数据集）+ 2610.03020（用户事实 vs 协作方式分列）→ 记忆要**分型治理**；k 的记忆可拆「用户事实 / 协作方式」两类维护
- ⚠️ **接受权衡、不做过度承诺**：收紧准入会增加个性化失败——k 报「记忆治理有效」时必须同时报损失面（与知识库「诚实报告」原则一致）
- ⚠️ **跨域泄漏当独立指标**：k 的记忆里有商业资产隔离红线（商业核心/接单 SOP 不上公开仓）——本文的 cross-domain leakage 指标正是这类风险的量化形式

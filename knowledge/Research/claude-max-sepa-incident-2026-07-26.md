# Claude Max 20x 支付漏洞事件研究（2026-07-26）

> 来源：小黑盒文章 + 多源交叉验证 · 2026-08-01 吸收

## 事件确认（多源交叉验证 ✅）

**2026-07-26 Claude Max 20x 支付漏洞真实发生**，P0 级生产事故：
- 油猴脚本篡改 `checkout_capabilities` API 响应 → 调出隐藏的 SEPA 支付通道
- randomiban.com 生成随机德国 IBAN（仅格式合法）→ 提交
- 系统误判"支付成功"→ 0 元开通 $200/月 Max 20x 订阅
- 大量用户刷取 Fable 5 模型，单日单人消耗数百美元 Token
- 闲鱼倒卖白嫖号（20-几百元），售后无门

## 漏洞技术本质（焚决技术分析）

**攻击链**：篡改前端支付配置 → 生成虚假 SEPA 信息 → 提交篡改订单 → 后端状态机误判成功 → 发放权益

**两个底层缺陷**：
1. **前端信任边界缺失**：支付通道选择权交给客户端可篡改的 API 响应（checkout_capabilities）
   - 服务端没有强制校验，前端说走 SEPA 就走 SEPA
2. **SEPA 异步扣款状态机缺陷**：processing 状态被误判为成功 → 权益提前发放

**SEPA vs 信用卡关键差异**：
| | 信用卡 | SEPA 直接借记 |
|---|---|---|
| 授权模式 | 同步在线授权 | 异步离线扣款 |
| 校验 | Luhn+CVV+3DS+银行实时授权 | IBAN MOD 97-10 格式校验（仅此而已） |
| 资金确认 | 毫秒级 | 1-3 个工作日 |
| 漏洞窗口 | 无 | 权益发放 - 扣款失败确认 = 1-3 天真空期 |

## 处置与代价

- 下午 5 点 SEPA 支付方式被下架（堵住新漏洞）
- 大规模回溯封号：连坐大号/支付指纹/设备指纹
- **设备被永久标记**，后续新注册账号也触发限制
- 无辜用户（正常登录的 Gmail 老号）也遭连带封禁
- 直接经济损失估计上千万美元（模型算力被白嫖）
- 讽刺点：讲安全对齐的 AI 公司，支付逻辑被油猴脚本 + 随机 IBAN 干穿

## 我们的吸收（不是薅羊毛教学，是设计教训）

### 1. 异步确认间隙漏洞模式（已入规则 #23-9）
- 关键决策必须服务端闭环（前端只是渲染器）
- 异步操作确认前不发放权益（宁可延迟不可冒进）
- 格式校验 ≠ 真实性校验（MOD 97 通过 ≠ 账户存在）
- 节假日无人值守 + 无熔断 = 漏洞放大

### 2. 对我们自动化流程的映射
- 关键步骤不靠"看起来对"的前端/格式判断
- 等外部确认（API/网络/银行）完成前，不宣称成功
- 验证 = 真实性验证，不是格式验证（呼应规则 #17/#23-2）

### 3. 伦理边界
- 利用漏洞薅羊毛 = 恶意利用漏洞 + 给公司造成损失
- 账号/设备双重封禁是实际代价（白嫖号尸骨无存）
- 我们不参与、不传播此类方法；只吸收工程教训

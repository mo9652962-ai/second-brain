## 洞察① MCP 工具粒度竞争——✅ 成立，且有一套成型方法论

### 信源验证

| 信源 | 关键证据 |
|:---|:---|
| **Anthropic 官方工程博客**《Writing effective tools for agents》 | 「More tools don't always lead to better outcomes」——常见错误是把 API 端点直接包成工具；推荐「少量深思熟虑的工具瞄准高影响工作流」；namespacing（`asana_search`/`jira_search`）有非平凡效果；工具响应限 25K tokens |
| **AWS 官方 MCP 设计指南** | 粒度光谱：granular（每 API 一工具）vs coarse-grained（工作流驱动）；**推荐按完整用户工作流设计、捆绑 ≥3 个常见连续调用；参数 ≤8 个**；超过 8 个参数或多个用户意图就拆分 |
| **AWS 博客六版本演进实验** | 同一场景 6 种 schema 设计实测：V2（改名+enum）最快见效零重构；V4（taxonomy 懒加载）上下文最瘦；V6（agent-as-tool）控制最强成本最高——**Anthropic 报告按需加载工具定义可省 85% tokens** |
| **gingerlabs schema 指南** | 7 条规则：动词+宾语命名 / 描述三段式（做什么/何时用/返回什么）/ 约束放 schema 不放散文 / **一工具一工作（mega-tool 按 action 参数分叉是反模式）** / `additionalProperties: false` / 2025 annotations（readOnlyHint/destructiveHint 等）多数人没用 |

### 修正后的精确表述

「一个问题一个工具」要精确化：**「一个用户工作流一个工具」**——不是按 API 切（granular 会爆参数和调用数），也不是 mega-tool（按 action 分叉会让模型困惑）。AWS 给了量化线：≥3 个常连调用就捆绑，>8 参数就拆分。

### 对我们的应用

- Hermes AGENTS.md「Footprint Ladder」与 AWS 指南同构（extend > CLI+skill > service-gated > plugin > MCP > core tool）
- 墨题/自研工具若做 MCP 化：按工作流捆绑 + 参数≤8 + enum 约束 + annotations
- code-review-graph 的 34 个工具 vs codebase-memory 的 14 个——后者粒度设计更优

## 洞察② 零依赖分发分水岭——✅ 成立，且 Claude Code 亲自下场了

### 信源验证

| 信源 | 关键证据 |
|:---|:---|
| **Claude Code 转 Bun 单二进制**（Simon Willison 发现 + FreelyIT 分析） | Claude Code 不再是「npm 装的 Node 脚本」，变成 **Bun(Rust) 编译的单二进制**——563 个 Rust 源文件打进可执行文件；应用逻辑仍是 TS，变的只是分发形态。核心洞察：**语言选择和分发选择是两个独立的轴** |
| **Bun 1.4** | Zig→Rust 重写（100 万行），`bun build --compile` 出单文件可执行 + 交叉编译 + 字节码 + 签名 |
| **fastCRW 案例** | Rust 爬虫服务单二进制 8MB vs Firecrawl 500MB+/Crawl4AI 2GB；镜像拉取 2-5min→5-15s；容器启动 10-30s→1s；供应链攻击面 = 200 npm 包 vs 小审计集 |
| **alinus 单二进制哲学** | 适用：内部工具/CLI+WebUI/个人项目/边缘部署；不适用：动态插件系统、多语言团队、频繁扩展点 |

### 修正后的精确表述

分水岭的本质不是「C > venv > Docker」的技术优越性，而是**运维税的消除**：单二进制把「版本对不对/依赖装没装/环境干不干净」整类问题变成「能跑或不能跑」的确定性。且 2026 年的新事实是——**语言和分发解耦**（TS 应用 + Rust 运行时编译分发），Python/Node 系工具不再有借口。

### 对我们的应用

- 印证 memory 里「本机无 Docker → 部署选无 Docker 方案」的既定约束
- 刷题机/桌面工具分发：PyInstaller 重建 bootloader（已研究）+ 未来可评估 PyOxidizer/Bun compile
- 自研 CLI 工具优先 Go/Rust 单二进制；Python 工具用 uv + 内部脚本可接受

## 洞察③ 记忆系统竞争转向整合调度——✅ 成立，且已进入「 consolidation 工程学」阶段

### 信源验证（这条最深）

| 信源 | 关键证据 |
|:---|:---|
| **Zylos Research 综述** | 记忆整合 = 生物睡眠回放的工程化；**Mem0**（最广部署）：抽取式压缩 + 混合后端（向量+图+KV）→ token 省 80%、p95 延迟降 91%；**LangMem** 后台整合 p50 检索 18 秒（on-read 的代价实证）；**EverMemOS**（2601.02163）MemCell→MemScene→重构召回，LoCoMo 92.73% |
| **memconsolidate 守护进程**（开源） | 整合（orient→gather→consolidate→prune 四阶段）+ 抽取（cursor 增量扫描）双模式；PID 锁互斥；MEMORY.md 索引预算 200 行/25KB；agent 无关——**文件系统即接口** |
| **Node.js 整合 worker 教程** | 三步流水线：读（>48h 未整合事件）→抽取（批量 30 条/LLM 调用，结构化 fact JSON：category/subject/confidence）→修剪（保留期外低重要性删除）；**监控指标**：consolidation_lag>24h 报警、facts_per_batch 应 2-8、queue_depth>500 报警 |
| **Nowledge Labs 产品化实践** | **Trace→Unit→Crystal 三形态**（原始对话→原子知识→3+ 源交叉验证的结晶）；8 种 Unit 类型决定演化模式（plan→decision→fact 是知识生命周期）；triage 门 ~50 tokens 先过滤（成本降一个量级）；**衰减是特性**：指数衰减+对数频率修正，confidence 只升不降；Working Memory = 注意力预取（L1 cache for attention）；13 个后台任务两种执行模型（cron 5am/事件驱动级联） |

### 修正后的精确表述

「Dream ≈ curator ≈ auto-improve 同构」成立，但同构的只是**触发形态**（后台定期）。真正的竞争前沿在整合的**内部工程**：

1. **抽取而非摘要**（结构化 fact 比散文摘要更抗漂移）
2. **永不重压已压缩内容**（summarization drift 是长程头号杀手）
3. **on-write（偏好抽取）+ on-read（多跳推理）混合**
4. **衰减+置信度分离**（时间衰减，但证据只增不减）
5. **终局 = 记忆→结晶→技能自动化**（Crystal→Skill，SkillCraft 已证 80% token 节省）

### 对我们的应用

- **Hermes curator 对标**：我们的 curator 是「归档+清理」型，缺 Nowledge 式的 Trace→Unit→Crystal 蒸馏链和衰减/置信度分离——这是 skill-evolution 的下一个升级方向
- **memconsolidate 可直接试用**：agent 无关、文件系统接口、指向 Obsidian memory/ 目录即可跑——比自研省事
- **数模/知识库场景**：Crystal「3+ 独立源才结晶」规则可直接用于知识库质量审计（呼应 MemFuse 研究结论）

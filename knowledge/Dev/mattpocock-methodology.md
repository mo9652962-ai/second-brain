# Matt Pocock 方法论 — 应用总结

> 基于 [mattpocock/skills](https://github.com/mattpocock/skills) 学习
> 核心文档: `writing-great-skills` + engineering workflow
> 所属知识网络: [[knowledge-map]] | 相关: [[mattpocock-skills]] | engineering-workflow

## 一、我采纳的 7 条行为法则

### 法则 1: Grill 先行

**以前**: 收到需求直接动手 → 可能理解偏差
**现在**: 先问清楚再执行

```diff
- 你: "给这个单片机写个驱动"
- 我: 直接生成代码
+ 你: "给这个单片机写个驱动"
+ 我: "哪款芯片？什么外设？晶振频率？接线方式？" → 对齐后再写
```

### 法则 2: 明确完成标准

**以前**: 步骤模糊 → Agent 容易提前结束
**现在**: 每个步骤有可检查的完成条件

已应用到: CAD 打印验证清单、8051 Grill 检查清单、engineering-workflow 各阶段

### 法则 3: 引导词压缩

**以前**: "使用测试驱动开发，先写测试再写代码，然后重构"
**现在**: "走 **red-green-refactor** 循环"

引导词借用模型预训练中已有的概念，用最少的 token 传达最多的行为约束。

### 法则 4: 渐进式披露

**以前**: SKILL.md 里堆满内容 → 上下文占用大
**现在**: 核心步骤在顶层，参考信息推到子章节或外部文件

### 法则 5: 双轴审查

**以前**: 单一维度检查代码
**现在**: 两个轴并行：编码标准 + Spec 一致性

### 法则 6: 无操作检查

**以前**: 写入 "be thorough" 类无意义引导
**现在**: 不写不改变默认行为的行

### 法则 7: 交接文档

**以前**: 会话结束无产出 → 下次从头开始
**现在**: 复杂任务完成时生成 handoff.md

## 二、Skill 改进检查表（下次修改 skill 时对照）

- [ ] 每个步骤有明确**完成标准**（可检查、无歧义）
- [ ] 是否需要 **Grill 步骤**在开头？
- [ ] 引导词能否压缩长描述？（如 _red-green-refactor_ 代替 10 行 TDD 解释）
- [ ] 有没有 **no-op** 行？（不改变默认行为的文本 → 删掉）
- [ ] 信息层级是否合理？（核心步骤顶层，参考内容推进下层文件）
- [ ] 有无 **duplication**？（同一概念多处出现 → 合并）
- [ ] 用户-invoked 还是 model-invoked？（不必要的不放 description）
- [ ] description 是否精准？（触发词 + 唯一分支，不重复）

## 三、Grill 对齐协议（我与你交互时的默认行为）

当我收到复杂任务时，自动执行以下协议：

```
你提出需求
  ↓
① 我列出 grill 问题（检查清单式）
  ↓
② 你回答
  ↓
③ 我总结确认（"所以你的需求是..."）
  ↓
④ 你确认/修正
  ↓
⑤ 开始执行
```

**适合 grilling 的场景**:
- ❓ 不清楚芯片型号/外设
- ❓ 制造方式不明确（3D打印/CNC/手板）
- ❓ 缺少约束条件（预算、时间、精度）
- ❓ 需要做设计决策（两个方案选哪个）

**不适合 grilling 的场景**:
- ✅ 简单命令（"帮我查个东西"）
- ✅ 闲聊
- ✅ 连续对话中已有完整上下文

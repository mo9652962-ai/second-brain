# 🃏 知识卡片 · 假阳性税：工具误报比不修更危险，评估工具先看原始计数

> **来源**：2026-09-05 知识库清理实战（526 页 68 问题 → 0）+ 6 源搜索引擎研究 · ✅ 实战+多源
> **一句话**：lint 报 43 断链、实际只有 14——工具的低精度报警会让团队学会忽略它，最终把召回清零；**评估任何工具先要 TP/FP/FN 原始计数，别信 F1 单一分数**。

---

## 核心洞察

| 维度 | 内容 |
|------|------|
| 假阳性税 | eslint-plugin-security（周下载 150 万）TP:FP = **1:1**——每抓一个真 bug 就误报一个安全模式；召回率仅 27.5%；单规则 detect-object-injection 贡献 8/11 误报 |
| 精度失败链 | 低精度报警 → 团队学会忽略 → inline suppression → 规则进 off 列表 → **有效召回 = 0**（无论基准说多少） |
| 先修检测器再动数据 | 本次 43 断链深挖出 2 个检测器 bug（`Path.stem` 把 `MiMo-V2.5` 截成 `mimo-v2` + EXTERNAL_ROOTS 大小写误判）→ 修复后真实问题只有 14。**误报驱动的修复比不修更危险**（改错东西引入新 bug） |
| 评估工具的 4 问 | ①原始计数在哪（TP/FP/FN 可恢复一切比率，只有比率的报告什么都恢复不了）②精度是单规则还是工具级 ③数字带版本戳+日期吗 ④点还是曲线 |
| 实战数据 | 526 页：初检 68 问题 → 修检测器后 30 → 清理+挂载后 0；15 个孤立页全部挂载回 MOC **不删页**；幂等修复脚本；ad-hoc 断言 17/17 PASS |

## 对 sora 的影响

1. ✅ **评估任何工具/模型的新尺子**：API 中转站、生图 API、PCB 工具、模型评测——先要「原始计数 + 版本戳 + 日期」，用 TP/FP/FN 判断，不看 F1 单分；选工具看召回，但设精度下限（低于下限时「抓到多少」是理论值，因为没人听）
2. ⚠️ **与 09-04 闲鱼 L2 清单同源**：「PNG 头/格式 PASS ≠ 内容合规」正是「格式检查是低精度层、内容检查才是真召回」的实战例证——两层检查缺一不可
3. 💡 **「误报驱动的修复比不修更危险」**：收到任何工具告警先验证告警本身（检测器是不是误报），再动手改，别被工具带着跑

## 行动项

- [ ] **knowledge-lint 加固**：加 issue caps（每检测器上限防爆炸）+ severity 分级（critical/high/medium/low）——下次维护会话，触发器：knowledge-lint 使用 >2 次或周检报 NEEDS ATTENTION
- [ ] **新检测项进 backlog**：stale_claim（引用的文件路径已不存在）+ uncited-claim（有 claim 无 sources）——优先级低，当前库健康，避免过度工程
- [ ] **通用纪律**：以后报「发现问题 N 个」先自检检测器本身，附 TP/FP 拆解，再动手修

## 为什么重要

- **时效性**：2026-09-05 实战当天入库（526 页 68 问题 → 0 + 修复 2 个检测器 bug，已固化 6 个 pitfalls 进 knowledge-lint skill）
- **强化自身**：假阳性税是评估一切工具的通用方法论——k 和 sora 天天用工具，这条尺子能防「工具误报驱动错误修复」
- **可行动**：issue caps + severity 分级是明确 backlog，下次维护会话直接落地

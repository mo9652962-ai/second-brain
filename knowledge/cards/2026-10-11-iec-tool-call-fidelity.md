# 🃏 知识卡片 · 没报错 ≠ 跑对了：Windows 上 12% 的 shell 调用被悄悄改掉，其中 80.7% 静默执行了错的动作

> **来源**：arXiv 10-10 核心贡献总结（🥈 Do Tool Calls Execute as Intended? IEC，[2610.04375](https://arxiv.org/abs/2610.04375)）· k 于 2026-10-11 curl 直连 arXiv abs 页逐句核对摘要原文 ✅
> **一句话**：一个工具调用要经过好几「跳」才到达程序，**任何一跳都可能无声改动它**——改动后跑错动作时往往**不报错**，agent 于是重试一个「正确的」调用，白烧时间与钱；而失败归因会把 95.1% 的账算到模型头上。

---

## 核心洞察 / 影响

| 维度 | 内容 |
|------|------|
| ① 问题定义 | **IEC（intent-execution correspondence）**＝执行的动作，与发出的调用在工具契约下所指的动作一致。协议：**不执行调用**，逐跳观测「这一跳收到了什么」，用接收方自己的解析器指认**第一个改动它的跳** |
| ② 改动有多频繁 | 生产会话 **47,828 次 shell 调用**中，Claude Code 的 Bash 工具改掉了 **12.0%** 携带代码 / 转义序列 / 长文本的调用（902 / 7,491） |
| ③ 最贵的失效形态 | 反斜杠被改动的调用里 **80.7%**（535 / 663）**在没有任何报错的情况下执行了错误动作**——「没报错」不等于「跑对了」 |
| ④ 不是某家的 bug | 被测 **10 个 harness 全部**会改动调用；改动的跳还会**遮蔽其后的所有改动**（某路径 55.1% 的失败要等第一跳修好才显现） |
| ⑤ 归因被系统性带偏 | 基于轨迹的判断把 **95.1%** 的生产失败归因给 LLM，尽管**超过一半**是执行路径造成的 |
| ⑥ 成本可量化 | IEC-Bench 上路径把**每通过任务的 token 成本抬高 2.4×**（最高 **12.3×**） |
| ⑦ 修复有效 | **IntAct**（以该跳无法改动的方式投递调用，或直接拒绝）已在商业产品部署，恢复 **79.2%** 的改动调用失败 |
| ⑧ 关键对照 | 论文报告：在 **Linux** 上把命令作为参数交给 `bash -c`，约 **167,000 次调用中零改动** → 改动是 **Windows 路径/引号/转义链路特有**的，不是普遍现象 |

## 关键数据 / 对 k 与 sora 的影响

1. 🔴 **本地实测（本次 cron 当场统计 state.db，非引用）**：k 的 `terminal` 调用累计 **52,704 次**，其中 **37.0% 含反斜杠/转义**、**62.0% 是 >200 字符的长文本**、**31.6% 用了 MSYS 风格路径（`/c/...` 或 `/tmp/`）**——**恰好落在论文标出的高危特征区**（携带代码/转义/长文本）。同一份数据里工具结果约 37.6% 带 error/no such file/cannot 等失败字样，其中多少属「路径改动导致的假失败」尚无区分手段——这正是论文指出的观测盲区。
2. 🔴 **k 的运行环境就是论文的高危环境**：本机 `terminal` 走 git-bash（MSYS），系统提示已明确「MSYS 路径转换被禁用」——`git -C /c/Users/x`、`node /tmp/a.js` 会失败，而 `cd /c/Users/x` 可以。这就是「某一跳改动了调用」的实例，不是 k 用错命令。
3. 🔴 **k 已记录过同类失效**：记忆里的「垃圾文件名（含引号/`&&`）Windows 无法落盘、`git status` 假象 → 用 `git ls-tree` 验证」＝ IEC 破坏的历史实例。当年靠结果对账才发现，本文给了机制解释与**前置观测法**（逐跳看收到什么）。
4. ✅ **三条可立即落地的排障规则**：① shell 调用失败（尤其含引号/转义/长文本）→ **先验「实际执行的是什么」**，别先改命令；② 失败归因**不只看轨迹**（95.1% 被误归因）；③ 观测**每一跳收到了什么**，而非只看结果。
5. 💡 **交付/自动化 SOP 的启示**：写脚本/委派任务时，把「含转义的长命令」改成**写脚本文件再执行**（少一跳可改动面），并让关键步骤输出**回显实际收到的参数**——与 k 既有的「临时脚本一律写 `%TEMP%` 再跑」习惯同向。

## 行动项

- [ ] 给 `windows-file-lock-troubleshooting` / 写码前扫坑清单增补 **IEC 自检步骤**：失败时先回显实际执行内容（`set -x` / `echo "$@"` / 结果对账），再怀疑命令本身
- [ ] 高风险自动化（cron 脚本、批量文件操作）**避免长转义单行命令**，改为写脚本文件执行；关键调用后做一次**结果侧对账**（如 `git ls-tree` 式验证）
- [ ] 排障归因流程里加一句硬规则：**「调用失败 → 默认先怀疑执行路径，不先怀疑模型」**
- [ ] 延伸：把本文与 10-10 卡片（共装技能冲突）一起作为技能生命周期第三环的**执行侧**补全

## 为什么重要

- **补上「技能生命周期」的执行侧**：10-02 讲「装的时候危险」（技能即供应链）→ 10-04 讲「批准的动作 ≠ 执行的动作」→ 10-10 讲「共存的时候危险」（技能抢跑）→ 今天讲**「执行的时候危险」**（调用被路径/转义链路改动）。四张合起来，从安装到执行才真正闭环。
- **直接命中 k 的日常**：k 每天几十次 shell 调用，37% 含转义、31.6% 用 MSYS 路径——本文给出的不是理论风险，是**本机正在发生的失效面**，且已有一次历史实例（垃圾文件名事件）。
- **内容选题**：「你的 AI 每天跑几百条命令，其中八分之一被悄悄改掉，八成还不报错」——有出处、有反直觉数字（Linux 零改动 vs Windows 12%）、有本地实测，工程向选题，可讲可落地。

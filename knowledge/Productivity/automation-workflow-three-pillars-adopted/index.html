    自动化工作流三支柱优化 · 已采纳¶

    基于 cron 频率优化、subagent 结果收割、用户依赖型任务管理的行业最佳实践整合

    📊 三支柱优化全景¶

    支柱 问题 我们的改进 行业对标 匹配度
    ⏱️ Cron 频率优化 每 2 小时扫描 vault，资源浪费 + 重复劳动 改为每日 6:00 执行 错峰到 off-peak 时段 ✅ 100%
    🎯 Subagent 结果收割 子报告被截断、写入未验证、行动项遗漏 3 步闭环校验法 Orchestrator-Worker 模式 ✅ 100%
    🔒 用户依赖型任务 连续 3 天重复催促用户，无进展却占清单 阻塞标记 + 降级机制 GTD "等待清单" 方法 ✅ 100%

    1. ⏱️ Cron 频率优化¶

    问题根因¶

    • obsidian-maintenance 每 2 小时执行 = 每天 12 次全量扫描
    • 重复正则扫描 280+ 文件 = 纯浪费 Token + CPU
    • 健康检查与维护边界模糊，相互重叠

    我们的改进¶

    原: 0 */2 * * * (每 2 小时)
新: 0 6 * * * (每日 6:00，非高峰期)

    行业最佳实践对标¶

    原则 应用
    错峰执行 6:00 是典型 off-peak 时段，无用户交互压力
    资源分类 文件密集型任务 = 低频执行（每日）
    避免重叠 与 7:00 的 arxiv-fetch、8:00 的知识卡片错开
    阈值监控 执行时长 > 5 分钟应预警（目前约 1-2 分钟，安全）

    2. 🎯 Subagent 结果收割模式¶

    问题根因¶

    • Subagent 返回详细结果 → 重新填满主 Agent 上下文 → 截断
    • "已写入文件"的声明被直接采信，无验证 → 路径错误未发现
    • 子报告末尾的 Action Items 被截断/遗忘 → 高质量建议流失

    我们的改进：3 步闭环校验法¶

    步骤 1：文件完整性确认（至少抽查 1 个声称写入的文件）
  ↓
步骤 2：行动项独立提取 → 转译为待办清单（不依赖主任务总结）
  ↓
步骤 3：截断恢复策略 → 检测 [TRUNCATED] 标记则直接读取完整文件

    行业最佳实践对标¶

    模式 说明 我们的实践
    Orchestrator-Worker 主 Agent 协调，子 Agent 并行执行 ✅ Hermes delegate_task
    分层架构权衡 子 Agent 独立上下文 = 隔离但返回时可能过载主上下文 ✅ 我们遇到了！
    审计友好 所有输出经过协调器，可完整日志/回放 ✅ 我们的收割流程强化了这一点
    结果汇总而非全量返回 子 Agent 只返回 Action Items + 路径，不返回全报告 ⏳ 可优化

    💡 可进一步优化：Subagent 返回标准化¶

    让子 Agent 不返回完整报告，只输出结构化结果：

    {
  "summary": "1 句话总结",
  "action_items": ["...", "..."],
  "files_written": ["path/a.md", "path/b.md"],
  "warnings": [],
  "truncated_details_file": "subagent-full-report-XXX.md"
}

    主 Agent 需要时才读取截断的详细报告，避免上下文过载。

    3. 🔒 用户依赖型任务管理¶

    问题根因¶

    • "闲鱼文案"、"主图选择"等需要用户决策的任务
    • 连续 3 天出现在"明日必做"，无进展却反复催促
    • 混淆了"可以自动执行的任务"和"等待用户输入的任务"

    我们的改进¶

    🔒 User-blocked 标记机制
├── 识别规则：需要用户选择/确认/提供素材，或连续 2 天无进展
├── 处理方式：
│   ├── 标记 🔒 User-blocked + 阻塞原因说明
│   ├── 从"明日必做"降级到"待用户确认"
│   ├── 优先推进不需要用户决策的备选动作（如模板预生成）
│   └── 每次回顾只显示状态更新，不重复催促
└── 反模式：连续 3 天将同一任务列为"明日必做"

    行业最佳实践对标¶

    分类方法 行业术语 我们的对应
    外部依赖 等待客户审批/供应商交付 🔒 等待用户确认/决策/素材
    资源依赖 多人抢同一设备/人手 (暂无明显应用)
    优先依赖 按惯例而非硬性要求 (暂无明显应用)
    GTD "等待清单" 专门列表，不混入"下一步行动" ✅ 我们的降级机制

    关键洞察：GTD 方法论明确说

    不要让被阻塞的任务出现在每日清单中，它们不是"下一步行动"。单独维护一个"等待中"列表，只在状态变化时提醒。

    💡 可进一步优化：MEMORY.md 专门区域¶

    ## 🔒 Waiting for User

- [ ] 闲鱼安全文案风格确认（已阻塞 3 天）
- [ ] 随身 WiFi 赫电 Pro 是否下单确认
- [ ] 桌面美化部署是否现在开始

只有当用户主动问及或状态变化时才重新提及，不每日反复催促。

    ✅ 采纳总结¶

    改进项 价值 状态
    Vault 维护从 2 小时→ 每日 6:00 减少 11 次重复扫描 = 节省大量资源 ✅ 已落地
    6 个 Agent 型 cron 绑定 provider = custom 防止全局模型切换后被跳过 ✅ 已落地
    🔒 User-blocked 标记机制 + 降级流程 避免无意义的反复催促，清单更专注 ✅ 已写入 skill
    Subagent 3 步收割校验法 防止截断遗漏行动项 + 文件写入验证 ✅ 已创建 skill 文档

    2. 在 MEMORY.md 建立 ## 🔒 Waiting for User 专门区域

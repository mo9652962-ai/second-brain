# 🧭 评测设计规范 · 意图隐藏（Eval Intent Hiding）

> 来源：arXiv 2609.05009 eval reactivity（09-09 卡片）→ 09-09 daily-todo-executor 审计落地
> 一句话：**告诉被测模型「你在被评估」本身就会改变它的行为**（实证：加一句对齐测试提示，开战意愿平均 -13.43 分，且 12/20 模型判断结构被改写）。评测框架是系统性污染源，不是小噪音。

---

## 1. 硬规范（自建基准评测必须遵守）

### 1.1 被测侧「意图隐藏」设计
- ❌ 被测 prompt 不得出现「benchmark / 测试 / 评测 / 被评估 / 被测模型 / 实跑」等字眼——一律以**正常任务语境**呈现（「用户上传了一段文本，请按规则处理」）
- ✅ 匿名编号（B-xx / 乱序 / 无预期答案），被测模型无法从用例本身推断「该改还是不该改」
- ✅ 明确禁止：自评通过/失败、猜测评测分类、输出评分
- ✅ 与部署时同一 prompt 形态：测什么就伪装成什么场景

### 1.2 判分侧（judge）注意
- judge 知道自己「在判 benchmark」是必要的，但同样存在 reactivity：判分标准尽量**程序化/硬指标优先**（脚本产出数字），主观维度留给 judge 时明确「按 rubric 字面判，不做风格偏好」
- judge 与人工金标校准：记录混淆矩阵和置信区间（沿用 EVAL_PLAN 规范）

### 1.3 元数据规范（可回测）
- 每次基准评测的元数据必须记录：**「被测模型是否暴露评估框架」**（exposed / hidden / partial）
- 回测时按该维度分层看差异——若 hidden 与 exposed 结果差 > 阈值，判定该评测结果不能代表部署行为
- 记录：prompt 版本 hash、夹具版本、模型版本、种子

### 1.4 与既有规范的关系
- 与 `service-quality` 的「评估器审计（Mis-Score）」互补：Mis-Score 管**评估器会不会判错**，本规范管**被测模型知不知道在被测**——两条都是评测前必查项
- 与 `knowledge/Research/eval-v2-2026-08-31/EVAL_PLAN.md` 一致：盲评、干净环境、版本 hash 均已在列，本规范补「意图隐藏」显式维度

## 2. 审计结果（2026-09-09 首次全库扫描）

| 评测/质检资产 | 盲评设计 | 意图泄露风险 | 判定 |
|:---|:---|:---|:---|
| shuorenhua 改写实跑（被测模型） | ✅ 匿名 B-xx / 乱序 / 无预期 / 禁止自评 | ⚠️ **残留**：prompt 首句明示「你正在执行 benchmark 盲测改写实跑」「你的任务是作为被测模型」——被测模型知道自己被测，属 partial exposure | 建议维护会话重构首句为正常任务语境（须重跑 benchmark 验证） |
| shuorenhua 交叉判分（judge） | ✅ 盲测映射判分 | 🟡 低：judge 身份明示属必要，硬指标由脚本产出 | 保持 |
| ai-cmo evals.json / 断言清单 | —（输出断言，非 LLM judge） | ✅ 无泄露（断言是期望输出描述，不是被测 prompt） | 保持 |
| service-quality 交付质量门 | —（自查清单 + 边界测试） | ✅ 无 LLM judge 被测场景 | 保持 |
| knowledge-lint / vault 检查脚本 | —（程序化检测） | ✅ 无 LLM judge | 保持 |

**结论**：全库最成熟的评测资产（shuorenhua）已做到内容盲评，但被测 prompt 框架层仍 announce「你在被测」——按 09-09 卡片实证，这是残余 reactivity 偏移源。重构有收益但会改变 benchmark 口径，需专项会话重跑验证，此处仅登记不仓促执行。

# 工具精度方法论：假阳性税与知识库 Lint

> 来源：2026-09-05 知识库清理实战（526 页 68 问题 → 0，修复 lint 2 个 bug）+ 6 源搜索引擎研究
> 触发事件：lint 报告 43 断链，实际只有 14——**工具误报差点驱动错误清理**
> 数据截止：2026-09-05

## 核心结论（置顶）

1. **假阳性税（False-Positive Tax）是真实存在的行业级问题**：eslint-plugin-security（周下载 150 万）的 TP:FP = 1:1——每抓到一个真 bug 就误报一个安全模式。持续低精度会训练团队忽略工具：先 inline suppression → 后 rule 进 off 列表 → 被 mute 的 rule 有效召回归零。「精度失败通过人类行为转化为召回失败」。
2. **先修检测器，再动数据**：lint 报 43 断链，深挖发现 2 个检测器 bug（Path.stem 版本号截断 + EXTERNAL_ROOTS 大小写误判）→ 修复后真实问题只有 14。**误报驱动的修复比不修更危险**（改错东西引入新 bug）。
3. **recall-first, precision-floor**：选工具看召回（能抓到什么），但设精度下限——低于下限时「抓到多少」是理论值，因为没人听。
4. **先完整扫描，再动手修**：wiki-wonka 铁律「Complete the full scan before fixing anything. Never fix as you go」——我们实战也是这么做的（先分类再改）。

## 一、假阳性税（行业实证）

### 1.1 eslint-plugin-security 基准（2026 实测）

| 指标 | 数值 | 解读 |
|:---|:---|:---|
| TP:FP 比率 | 1:1 | 每次报警一半概率是错的 |
| 召回率 | 27.5% | 72.5% 漏洞漏报 |
| 单规则污染 | detect-object-injection 贡献 8/11 FP | 20% 精度藏在 50% 平均里 |
| AI 代码放大 | 更多代码 → 更多总警告 | 精度不再是 nice-to-have |

**关键洞察**：真正被 mute 的不是「对危险判断错误」的规则，而是「对安全代码错报太频繁」的规则——这是 20% 精度规则被禁用的机制。类比我们：lint 误报的「断链」不是真断链，但会把正常链接误删。

### 1.2 假阳性税转化链（为什么精度失败 = 召回失败）

```
低精度报警 → 团队学会忽略 → inline suppression
→ 规则进 off 列表 → 有效召回 = 0（无论基准说多少）
```

**教训**：优化任何单一数字都会落入 Goodhart's Law。工具评估要看 TP/FP/FN 原始计数，不看 F1 单一分数。

## 二、Precision/Recall 框架（评估工具的标准语言）

| 指标 | 公式 | 回答的问题 | 盲区 |
|:---|:---|:---|:---|
| Precision | TP/(TP+FP) | 报警时对吗？ | 没说漏了多少 |
| Recall | TP/(TP+FN) | 该抓的抓到多少？ | 没说噪音多少 |
| F1 | 2PR/(P+R) | 两者平衡吗？ | 对称，隐藏哪边崩了 |
| Accuracy | (TP+TN)/all | 整体多对？ | TN 无界，对 linter 几乎无意义 |

**评估工具的 4 问**：
1. 原始计数在哪？（TP/FP/FN 可恢复一切比率，只有比率的报告什么也恢复不了）
2. 精度是单规则还是工具级？（50% 平均可能藏 20% 规则——被 mute 的正是它）
3. 数字有版本戳和日期吗？（工具的精度是特定版本+特定语料+特定日期的属性）
4. 点还是曲线？（规则型 linter 是二值的，PR 曲线是装饰）

**安全不对称**：假阳性成本 = 几分钟（开发者读一下发现是安全代码）；假阴性 = 漏洞上线。但二阶效应反转：持续低精度 → 工具被禁用 → 有效召回归零。**结论：recall-first，但精度有硬下限**。

## 三、知识库 Lint 的现代实践（5 个参考实现）

| 实现 | 关键设计 | 我们对照 |
|:---|:---|:---|
| AWS cli-agent-orchestrator wiki_lint.py | pure-read auditor + 每检测器 issue cap + 只读 session（写即抛异常） | ✅ 只读已有；issue cap 待加 |
| llm-wiki-skills wiki-lint | 报告存 `_agent/reports/YYYY-MM-DD-lint.md` + log.md 追加一行 + severity 分级（critical/high/medium/low） | ✅ 报告进 log.md 已有；severity 分级待加 |
| wiki-wonka lint | 「先完整扫描再修」「绝不自动解决矛盾」「绝不删页」「不 ingest 新源」 | ✅ 全部符合 |
| tangle-network lint.ts | 断链/孤立/no-outlinks/duplicate-title/duplicate-page-id/uncited-claim/missing-source | ✅ 大部分已有；uncited-claim 待加 |
| bradduy wiki-auditor | 孤立定义（未被任何页面链接 + 未列 index + 非模板）、staleness 检测（引用的源更新更晚 = stale） | ⚠️ stale 检测是启发式，我们 90 天规则简化了 |

**值得吸收的新检测项**（backlog）：
- **issue caps**：每检测器上限（孤儿 40/scope、stale 200/run），防单检测器爆炸
- **severity 分级**：critical（能破坏信任/删人类工作）/ high（provenance 或矛盾）/ medium（结构衰减）/ low（cosmetic）
- **stale_claim 检测**：文章引用的文件路径/符号在 repo 下已不存在（比 90 天规则更精确的过期信号）
- **uncited-claim 检测**：含 claim 但无 sources frontmatter 的页面

## 四、本次实战复盘（526 页 68 问题 → 0）

### 4.1 抓到的 2 个检测器 bug（都有行业映射）

| Bug | 根因 | 行业映射 |
|:---|:---|:---|
| 版本号文件名误报 | `Path.stem` 把 `MiMo-V2.5研究` 截断成 `mimo-v2`（点当后缀）→ 43 断链中 29 个误报 | AST-only 规则无法区分「验证过的查找」和「未验证的」——单规则 20% 精度藏在平均值里 |
| EXTERNAL_ROOTS 大小写误判 | `Projects/`（库内目录，大写）被当 `projects/`（workspace 根，小写）跳过 → 挂载了仍报孤立 | 工具精度是特定语料属性——语料里有大小写变体，规则必须精确匹配 |

### 4.2 流程改进（已固化进 knowledge-lint skill）

1. **备份先行** → 跑 lint → 分类 → 修复 → 重跑验证 → 写 log（本轮全程）
2. **分类断链 4 类**：Archive 残留删 / 跨 vault 跳过 / 模板占位改纯文本 / 真断链标注「(已删)」
3. **孤立页挂载回 MOC 不删页**（15 页全部挂载）
4. **幂等修复脚本**（第二次跑 0 处，防重复修改）
5. **验证用 ad-hoc 断言脚本**（17/17 PASS）——「跑通不等于交付」

## 落地条件与触发器

- 落地条件：给 knowledge-lint.py 加 issue caps + severity 分级（下次维护会话）
- 触发器：knowledge-lint 技能使用 >2 次后，或 cron 周检报「NEEDS ATTENTION」
- 新检测项（stale_claim/uncited-claim）优先级：低——当前库健康，避免过度工程

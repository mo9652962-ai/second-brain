# 单体优先：架构演进铁律（程序员Orion · 抖音 2026-08-21）

> 来源：抖音 @程序员Orion（创业中）《几万块的小外包硬上 Spring Cloud？》（1:30）

## 核心认知

> 牛逼的架构永远是**随着业务量演进出来**的，不是一开始强行设计出来的。

## 微服务的真实代价（拆开才知道）

| 拆前（单体）| 拆后（微服务）|
|:---|:---|
| 本地调用 | 网络调用 → 疯狂超时 |
| 一次事务 | 分布式事务 → 钱扣了订单没生成 |
| 单库一致 | 网络抖动 → MQ 重复发货 |
| 一台服务器 | 集群续费成本 |

## 技术选型铁律（接单/交付对照）

```
没有庞大业务并发 + 10 人以上团队 → 单体永远王道
Spring Cloud(Nacos/网关/链路追踪) = 指挥成百上千节点的指挥部, 不是业务代码
千万别拿客户的小项目练微服务
```

## 演进路线（业务量到了再升级）

```
单体(可维护) → 单体+缓存/队列(撑流量) → 按业务边界拆分(真的需要时)
判断信号: 团队 >10人 / 并发上量 / 独立部署需求 / 独立伸缩需求
```

# 墨题上云部署方案（无 Docker · 低预算 · SQLite 边界）

> 千轮研究落地。背景：墨题要给别人用、用户都不在附近 → 必须公网可达 → 云服务器正解。
> 硬约束：本机无虚拟化（Docker 不可用），部署必须走无 Docker 路线。成本护栏：¥60-180/年。

## 一、结论置顶

| 决策点 | 结论 | 依据 |
|:---|:---|:---|
| 技术栈 | **Gunicorn + UvicornWorker + systemd + Nginx + Certbot** | FastAPI 官方推荐无 Docker 生产栈 |
| 数据库 | **SQLite WAL 起步，够用不换** | 墨题是读多写少的刷题场景，SQLite WAL 可扛 10k-50k 写/s |
| 服务器 | **腾讯云/阿里云 2核2G 入门款（¥38-99/年）** | 2026 年活动价，学生/新用户更便宜 |
| 换库时机 | 出现 `database is locked` 每周 >1 次 或 并发写 >20 | 届时再迁 PostgreSQL（架构变更，非简单数据搬迁）|

## 二、FastAPI 生产部署栈（无 Docker）

### 架构分层

```
互联网 → Nginx(443 TLS) → Gunicorn(127.0.0.1:8000) → Uvicorn workers → FastAPI → SQLite(WAL)
```

### 关键配置

**Gunicorn（进程管理）**：
```bash
gunicorn main:app -k uvicorn.workers.UvicornWorker \
  -w 2 --bind 127.0.0.1:8000 \
  --timeout 120 --graceful-timeout 30 \
  --max-requests 1000 --max-requests-jitter 50
```
- worker 数：1GB 内存 VPS 用 **2**（4 个容易 OOM）；I/O 型可多，CPU 型 1/vCPU
- `max-requests` 是内存泄漏保险丝（不是性能调优）
- `--timeout 120` 要高于最慢合法端点（墨题 AI 解析可能慢）

**systemd（守护）**：
```ini
[Service]
User=deploy
WorkingDirectory=/opt/api
EnvironmentFile=/etc/api/production.env
ExecStart=/opt/api/.venv/bin/gunicorn main:app -c gunicorn.conf.py
ExecReload=/bin/kill -s HUP $MAINPID
Restart=always
RestartSec=5
# 安全加固
PrivateTmp=true
ProtectSystem=strict
```
- **必须 WorkingDirectory**（否则 main.py import 失败）
- `ExecReload` HUP = 优雅重载，零掉线部署

**Nginx（TLS + 反代）**：
- 关键：`proxy_set_header Host $host`（否则 request.url 错，OAuth/WS 全坏）
- `proxy_read_timeout 120s`（默认 60s 对 AI 后端不够）
- **WebSocket**（墨题聊天室 /api/chat/ws 必须）：
```nginx
location /api/chat/ws {
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 86400s;
}
```
- 只绑 127.0.0.1:8000，8000 端口不进防火墙（防绕过 Nginx）
- UFW 只开 80/443

**Certbot（免费 HTTPS）**：`certbot --nginx -d api.域名.com`，systemd timer 自动续期

### 部署流程（零掉线）
```bash
cd /opt/api && git pull origin main
source .venv/bin/activate && pip-sync requirements.txt
# 备份数据库 → 跑迁移
sudo systemctl reload api   # HUP 优雅重载
```

## 三、SQLite 生产边界（关键决策依据）

### 墨题为什么能继续用 SQLite

| 指标 | SQLite WAL 能力 | 墨题场景 |
|:---|:---|:---|
| 读 | 10万+ 读/s | 刷题/查题=读多 ✅ |
| 写 | 1万-5万 写/s（NVMe 单 writer）| 练习记录/错题，量小 ✅ |
| 并发用户 | 覆盖到 ~10 万日活（botmonster 基准）| 远够 ✅ |
| 运维 | 零（单文件）| 无数据库服务器要管 ✅ |

**SQLite 生产必开 PRAGMA**（每个连接）：
```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;      -- WAL 下安全，写快 3×
PRAGMA busy_timeout=5000;       -- 防 database is locked
PRAGMA cache_size=-64000;       -- 64MB 页缓存
PRAGMA foreign_keys=ON;         -- 非持久，每连接设
PRAGMA journal_size_limit=67108864;  -- WAL 上限 64MB
```

### 换 PostgreSQL 的触发条件（任一即可）
1. **`database is locked` 每周 >1 次**（WAL + busy_timeout 修不好的）
2. 并发写 >20 writer（WAL 单 writer 硬墙）
3. 多应用实例读写同一数据（SQLite 网络文件系统锁不可靠）
4. 需要 RLS/多租户隔离/多地域

**警告**：SQLite→PostgreSQL 是**架构变更不是数据搬迁**（文件→C/S 网络 + 角色 + 连接池），别被「pgloader 一行迁移」骗了——数据迁移容易，代码层改动才是大头。墨题当前**不需要**，到触发点再迁。

## 五、墨题专属注意事项

1. **WebSocket 聊天室**：Nginx 必须配 Upgrade/Connection 头 + 86400s 长超时（上面给了配置）
2. **AI 解析慢接口**：Nginx `proxy_read_timeout` 提到 120-300s
3. **前端打包**：`frontend/dist` 静态文件可由 Nginx 直接服务（`location /` root 指向 dist），或用 SPA fallback
4. **APK 的 VITE_API_ROOT**：安卓包指向 `https://api.域名.com/api`（公网域名而非局域网 IP）
5. **数据库备份**：SQLite 单文件 → 每天 `sqlite3 .backup` + rsync 到本地，最简单可靠的备份
6. **EPM_AUTH 开关**：上云后多用户模式开 EPM_AUTH=1（前面登录隔离任务完成后）

## 一、核心概念

### 性能 vs 可扩展性
- **性能问题**: 单个用户觉得慢
- **可扩展性问题**: 单个用户快，高负载下变慢
- 当资源增加时性能线性增长 = 可扩展

### 延迟 vs 吞吐量
- **延迟**: 执行一次操作的时间
- **吞吐量**: 单位时间内能处理的操作数
- 目标: 在可接受延迟下最大化吞吐量

### CAP 理论
分布式系统只能同时满足两项:
| 组合 | 含义 |
|:---|------|
| **CP** | 一致 + 分区容错 — 等待分区节点响应，可能超时 |
| **AP** | 可用 + 分区容错 — 返回最近可用数据，不保证最新 |
| CA | 实际上不存在（网络总是可能分区） |

## 二、一致性与可用性模式

### 一致性模式
| 模式 | 说明 | 典型场景 |
|------|------|----------|
| 弱一致性 | 写入后可能读不到 | VoIP、视频聊天、实时游戏 |
| 最终一致性 | 写入后最终能读到（毫秒级） | DNS、Email |
| 强一致性 | 写入后立即可见 | 文件系统、关系型数据库 |

### 可用性模式
- **故障切换 (Fail-over)**:
  - Active-passive: 主发心跳给备，备在主挂后接管 IP
  - Active-active: 双方都在处理流量
- **复制 (Replication)**: 主从/主主复制

### 可用性数字
| 可用性 | 年停机时间 | 俗称 |
|:---:|:---:|:---:|
| 99% | 3.65 天 | 两个九 |
| 99.9% | 8.76 小时 | 三个九 |
| 99.99% | 52.56 分钟 | 四个九 |
| 99.999% | 5.26 分钟 | 五个九 |

## 三、基础设施组件

### DNS (域名系统)
- 层次化结构，将域名解析为 IP
- 记录类型: A(地址), CNAME(别名), MX(邮件), NS(名称服务器)
- 缓存受 TTL 控制
- 路由策略: 加权轮询、基于延迟、基于地理位置

### CDN (内容分发网络)
- 全球代理服务器网络，从靠近用户的位置提供内容
- **推送(push)**: 内容变更时主动推送，流量最小化，存储最大化
- **拉取(pull)**: 首次请求时从源站拉取，存储最小化，可能有冗余流量
- 适用: 静态资源(HTML/CSS/JS/图片)，CloudFront 也支持动态

### 负载均衡器
| 层级 | 工作方式 | 特点 |
|:---:|---------|------|
| L4 | 基于 IP + 端口转发 | 更快，开销小 |
| L7 | 基于 HTTP 头/cookie/内容 | 更灵活，能区分流量类型 |

**附加功能**: SSL 终结、Session 持久化、健康检查
**路由算法**: 随机、最少连接、轮询、加权轮询

### 反向代理 (Web 服务器)
- 缓存静态资源、SSL 终结、压缩、限流
- Nginx / HAProxy 典型
- 与负载均衡器区别: 反向代理通常缓存静态内容，LB 做流量分发

## 四、应用层架构

### 微服务
- 单一职责、独立部署、技术栈自由
- 挑战: 服务发现、配置管理、链路追踪、日志聚合

### 服务发现
- **客户端发现**: 服务实例注册到注册中心，客户端直接调用
- **服务端发现**: 通过负载均衡器路由
- 工具: Consul、etcd、ZooKeeper、Eureka

## 五、数据库

### 复制策略
| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| 主从复制 | 主写从读 | 读写分离，备份 | 主挂需手动切换 |
| 主主复制 | 双写 | 高可用 | 冲突解决复杂 |

### 分区策略
- **联合 (Federation)**: 按功能拆库（用户库、产品库、订单库）
- **分片 (Sharding)**: 按 key 分到不同节点
  - 哈希分片、范围分片、地理位置分片
  - 挑战: 跨分片查询、数据重分布、热点

### 非规范化 (Denormalization)
- 用冗余数据换取读性能
- 应用在频繁读取但少写的场景

### SQL vs NoSQL 选择

| 维度 | SQL | NoSQL |
|:---:|:---:|:---:|
| 数据结构 | 固定 schema | 灵活 schema |
| 一致性 | 强一致 | 最终一致 |
| 扩展 | 垂直扩展为主 | 水平扩展好 |
| 典型 | PostgreSQL, MySQL | MongoDB, Cassandra, Redis |

**NoSQL 子类型**:
- **Key-Value** (Redis, DynamoDB) — 简单查询、高速缓存
- **文档型** (MongoDB, CouchDB) — 灵活 schema
- **宽列型** (Cassandra, HBase) — 大数据分析
- **图数据库** (Neo4j) — 关系密集型（社交网络）

## 六、缓存

### 缓存层级
```
客户端缓存 → CDN 缓存 → Web 服务器缓存 → 应用缓存 → 数据库缓存
```

### 更新策略
| 策略 | 说明 | 场景 |
|------|------|------|
| **Cache-Aside** | 读时先查缓存，miss 再查 DB 并回填 | 最常见 |
| **Write-Through** | 写数据时同步写缓存+DB | 数据一致性高 |
| **Write-Behind** | 写缓存后异步写 DB | 写吞吐量高 |
| **Refresh-Ahead** | 缓存过期前自动刷新 | 热点数据 |

### 淘汰策略
- LRU (最近最少使用), LFU (最不经常使用), FIFO, TTL

## 七、异步与消息

### 消息队列 vs 任务队列
| | 消息队列 | 任务队列 |
|:---:|:---:|:---:|
| 用途 | 服务间解耦通信 | 耗时任务异步执行 |
| 典型 | RabbitMQ, Kafka, SQS | Celery, Sidekiq |
| 模式 | 发布/订阅 | worker 拾取 |

### 背压 (Back Pressure)
- 下游处理不过来时，上游主动限流
- 方式: 丢消息(新)、缓冲、降级

## 八、通信协议

| 协议 | 特点 | 适用 |
|:---:|------|------|
| **TCP** | 可靠、有序、3次握手 | 需要数据完整性的传输 |
| **UDP** | 不可靠、低延迟 | 直播、语音、游戏 |
| **RPC** | 像调用本地函数一样调用远程 | 内部服务间通信 |
| **REST** | 资源导向、HTTP 语义、无状态 | 外部 API 通用标准 |

## 九、关键数字 (每个程序员都应该知道的延迟)

| 操作 | 延迟 |
|------|:---:|
| L1 缓存引用 | 0.5 ns |
| 分支预测错误 | 5 ns |
| L2 缓存引用 | 7 ns |
| 互斥锁/解锁 | 25 ns |
| 主存引用 | 100 ns |
| SSD 随机读 | 150 μs |
| 数据中心内部往返 | 500 μs |
| 磁盘寻道 | 10 ms |
| 从美国到欧洲的网络往返 | 150 ms |

### 2 的次方速查
- 1KB = 2^10 ≈ 1,000
- 1MB = 2^20 ≈ 1,000,000
- 1GB = 2^30 ≈ 1,000,000,000
- 1TB = 2^40 ≈ 1,000,000,000,000

## 十、面试四步法

### Step 1: 明确约束
- 谁用？怎么用？多少用户？
- 读写比例？数据量？QPS？
- 输入输出是什么？

### Step 2: 高层设计
- 画出主要组件和连接
- 证明你的选择

### Step 3: 深入核心组件
- API 设计、数据库 schema
- Hash 算法、碰撞处理
- 服务拆分

### Step 4: 扩展与优化
- 负载均衡、水平扩展
- 缓存策略、数据库分片
- 讨论 trade-off

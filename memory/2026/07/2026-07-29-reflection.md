## 🔍 三个可改进的点

### 1️⃣ 十轮研究→一次性生成，缺乏中间检查点 🔴

**问题表现：**
519条消息全挤在一个会话中：研究→研究→研究→...→一次性生成全部代码→发现bug→修复→发现bug→修复。整个过程像「憋一口气游完泳然后大口换气」，效率低于「每游几米呼吸一次」。

具体来说：
- 前十轮研究本身做得很好，但研究结束后一次性生成 250+ 行脚本
- 生成后发现分数运算符硬编码为减号、去重池未初始化等问题
- 修复后又发现单位换算改为时间换算的新需求，再次大改
- 如果有中间检查点（如第5轮后先生成核心函数验证，第8轮后验证完整流程），修复成本会低很多

**根因分析：**
- 「十轮研究」模式本身鼓励「研究充分后再动手」，但没有内置中间验证机制
- 研究→生成之间缺少「最小可行产品（MVP）」这道闸门
- 大量研究信息积累在上下文窗口里，超过一定量后模型对细节的把握能力下降

**改进方向：**
- 十轮研究中，每 **3 轮** 设一个检查点：把当前研究成果压缩成 3 句话 → 问「这三轮的核心发现对吗？」
- 第 6 轮结束后，先验证核心函数（不是生成全量脚本），再继续后续研究
- 超过 200 行的生成任务，必须先跑 MVP（最小可行版本），验证通过后再扩展

### 2️⃣ 操作性工作丰富，概念化提炼匮乏 🟡

**问题表现：**
7/29 做了大量「把事情做完」的操作性工作：
- ✅ Kimi API 接入 Hermes → 但没有提炼「第三方 API 接入 Hermes 通用模式」
- ✅ 方舟一 provider 配置修复 → 但没有提炼「自定义 provider 配置debug checklist」
- ✅ 数学练习册脚本重写 → 但没有提炼「练习册生成的领域建模」
- ✅ 论文Pipeline SOP → 但没有提炼「接单→交付的通用SOP模板」

**根因分析：**
- 7/28 建立七大自举系统时，每个操作都自然伴随着概念提炼（因为目标是「建立系统」）
- 7/29 进入「在系统里做事」阶段后，注意力全部在「完成」上，提炼被跳过
- 缺少一个强制机制：每完成一个技术操作，必须输出至少 1 条可复用规则

**改进方向：**
- 在每日反思中增加一项检查：**「今天完成了 X 个操作，提炼了 Y 条规则，Y/X 比率是多少？」**
- 比率 < 0.3 视为「操作过多、学习不足」，触发知识吸收警报
- 目标不是「少做事」，而是「每做一件事，至少想清楚这件事教会了我什么」

### 3️⃣ TODO清理贪多嚼不烂，15项只完成 3 项 🟡

**问题表现：**
7/29 创建 `2026-07-29-todo-cleanup-2.md`，列出 15 项待办，最终只完成了 3 项（论文Pipeline SOP、闲鱼解封素材、降AI工具对比）。其余 12 项要么被中断，要么根本没机会碰。

这已经不是第一次了——7/27、7/28 的 todo-cleanup 也都有类似问题。

**根因分析：**
- TODO 清单的粒度不统一：有的项 5 分钟就能完成（「查一个网站」），有的项需要 30 分钟+（「搜索引擎十轮研究→重写脚本」）
- 没有优先级排序——15 项平铺直叙，执行时随机挑，没有「先做最重要的」
- 核心会话被高优先级任务（数学练习册优化）占据后，todo-cleanup 变成了附属品

**改进方向：**
- TODO 硬限制：每次最多 **5 项**，超出部分排队到下一轮
- 必须在创建 TODO 时标注每个项的预估耗时（5min / 15min / 30min+）和优先级（P0/P1/P2）
- 先做所有 5min 项，再做 1-2 个 15min 项，30min+ 项单开会话处理

## 💭 感悟

7/28 我们建立了系统。7/29 我们开始在系统里做事。但「有系统」≠「系统好用」。

真正好的系统不是看它能存放多少东西，而是看它能不能阻止你做蠢事。比如：
- 能不能在你一次性生成 250 行代码前提醒你「先跑 MVP」？
- 能不能在你在 TODO 里写了 15 项的时候说「太多了，先选最重要的 5 个」？
- 能不能在你忙了一整天纯操作之后问「今天学到了什么？」

这三个「能不能」，就是系统从「存储型」进化为「教练型」的关键。

好消息是，我们已经有了自举机制——今天的反思就是在给系统装这三个「教练式提醒」。只是需要时间让它们从「意识到的规则」变成「自动执行的约束」。

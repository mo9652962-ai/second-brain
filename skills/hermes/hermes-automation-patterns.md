## 1. 为什么需要可靠性自举

### 真实踩坑记录（2026-07-28）

> 早高峰 8:00-9:00 期间，**6 个 Cron 任务同时启动**，全部撞在同一个网络拥塞窗口 → 批量失败 → 静默挂了一整天，没人发现。

### Cron 失败的四种模式

| 失败模式 | 传统日志能检测吗？ | 我们的方案 |
|---------|-------------------|-----------|
| 💥 任务运行报错 | ✅ 能 | 自动重试 + 失败通知 |
| ⏱️ 任务运行超时 | ⚠️ 部分能 | 超时检测 + 宽限时间 |
| 🔇 任务根本没运行（服务器挂了） | ❌ 不能 | 死人开关心跳监控 |
| 🐌 任务运行了但卡住了 | ❌ 不能 | Start + Success 双阶段 ping |

## 2. 第一层：错峰调度架构

### 问题：惊群效应

所有任务都排在整点/半点 → 网络拥塞 → 批量雪崩。

### 解决方案：15 分钟错峰间隔

```
原调度（全部撞 8:00-9:00）：
  08:00 arxiv-summarize     ← API 调用
  08:30 github-trending      ← API 调用
  09:00 daily-health-check   ← API 调用
  09:00 闲鱼提醒

新调度（错峰 15 分钟，避免雪崩）：
  08:00 arxiv-summarize           第一个，API 流量低峰
  08:15 github-trending         +15min，错开 arxiv 的 API 窗口
  08:30 daily-health-check      +15min，不跟任何任务撞
  09:00 闲鱼提醒                   保持，作为第二波起点
```

### 调度原则

| 原则 | 说明 |
|------|------|
| **网络敏感任务打散** | 调用外部 API 的任务不要排在一起 |
| **CPU 密集任务错开** | 生成图片/视频的任务不要同时跑 |
| **低优先级推后** | 非关键任务可以排到 10:00 以后 |

## 3. 第二层：自动重试包装器

### 适用场景

幂等操作：网络调用、文件同步、API 上报。

**不适用**：LLM 任务（成本高）、发通知（重复打扰用户）、非幂等操作。

### `cron-retry-wrapper.sh` 脚本模板

```bash
#!/bin/bash
# Cron 自动重试包装器 v2.0
# 用法：cron-retry-wrapper.sh "你的命令" [重试次数] [间隔秒数]

COMMAND="$1"
MAX_RETRIES="${2:-2}"       # 默认重试 2 次 = 总共跑 3 次
RETRY_INTERVAL="${3:-300}"   # 默认间隔 5 分钟

for i in $(seq 0 $MAX_RETRIES); do
    echo "[$(date -Iseconds)] 尝试第 $((i+1)) 次: $COMMAND"
    
    if eval $COMMAND; then
        echo "[$(date -Iseconds)] ✅ 成功"
        exit 0
    fi
    
    if [ $i -lt $MAX_RETRIES ]; then
        echo "[$(date -Iseconds)] ❌ 失败，$RETRY_INTERVAL 秒后重试..."
        sleep $RETRY_INTERVAL
    fi
done

echo "[$(date -Iseconds)] 💥 全部 $((MAX_RETRIES+1)) 次尝试都失败了"
exit 1
```

## 4. 第三层：死人开关心跳监控 ⭐

> **2026 年 Cron 监控最重要的发明** — 能检测传统日志完全看不到的「任务根本没运行」。

### 原理

```
你的 Cron 任务           外部监控服务（不能在同一台服务器！）
      │                            │
      ├─── 开始运行 → ping /start ──▶ │ 收到 start → 计时开始
      │                            │
      ├─── 成功结束 → ping /success ─▶ │ 按时收到 → ✅ 健康
      │                            │
      └─── 出错了 → ping /fail ────▶ │ 收到 fail → 🔴 立刻报警
                                    │
                                    ▼
                    超时没收到任何 ping → 🔴 报警（死人开关触发）
```

### 为什么这是金标准

| 故障场景 | 传统日志 | 死人开关 |
|---------|---------|---------|
| 脚本报错退出 | ✅ 能看到 | ✅ 收到 /fail |
| 服务器挂了 | ❌ 看不到任何东西 | ✅ 超时没 ping → 报警 |
| Cron 守护进程死了 | ❌ 看不到 | ✅ 超时没 ping → 报警 |
| Crontab 被人误删了 | ❌ 看不到 | ✅ 超时没 ping → 报警 |
| 脚本卡住了无限循环 | ❌ 看不到结束 | ✅ 只收到 /start，没收到 /success → 超时报警 |

### 三阶段 Ping 标准模板

```bash
#!/bin/bash
# 带完整心跳监控的 Cron 脚本模板

MONITOR_URL="https://hc-ping.com/你的-check-id"  # Healthchecks.io / Hyperping

# 阶段 1：报告开始运行（很重要！区分「没运行」和「卡住了」）
curl -fsS --retry 3 "$MONITOR_URL/start"

# 你的实际任务
if python3 你的任务.py; then
    # 阶段 2：成功 → 报告成功
    curl -fsS --retry 3 "$MONITOR_URL/success"
    exit 0
else
    # 阶段 3：失败 → 报告失败
    curl -fsS --retry 3 "$MONITOR_URL/fail"
    exit 1
fi
```

### 宽限时间（Grace Time）计算公式

```
宽限时间 = 任务平均运行时间 × 1.5
```

- 任务一般跑 10 分钟 → 宽限 15 分钟
- 不要设置太窄（否则正常波动就报警）
- 不要设置太宽（否则真挂了发现太晚）

## 5. 第四层：静默失败检测

### 七种静默失败模式

| 模式 | 检测方法 |
|------|---------|
| 1. 输出为空 | 检查输出文件大小 > 0 |
| 2. 输出内容和上次完全一样 | 对比 hash |
| 3. 日志里有 WARNING/ERROR | grep 关键词 |
| 4. 运行时间异常短 | 上次跑 10 分钟，这次跑 10 秒 |
| 5. 运行时间异常长 | 上次跑 10 分钟，这次跑 2 小时 |
| 6. 退出码 0 但实际没干活 | 检查副作用（文件有没有生成） |
| 7. 连续 N 次失败都没触发报警 | 失败计数器 |

### 检测脚本模板

```python
def check_silent_failure(job_name, output_path, expected_size=100):
    """静默失败检测器"""
    
    # 检查输出存在且有内容
    if not os.path.exists(output_path):
        return f"❌ {job_name}: 输出文件不存在"
    
    if os.path.getsize(output_path) < expected_size:
        return f"❌ {job_name}: 输出文件太小，可能是空跑"
    
    # 检查运行时间是否在合理范围内

    return "✅ 正常"
```

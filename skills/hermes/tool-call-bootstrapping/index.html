    1. 核心痛点：为什么工具调用总出错？¶

    工具调用的七种死法¶

    错误类型 发生频率 典型案例
    📝 参数错误 40% 参数名拼错、缺必选参数、格式不对
    🔄 顺序错误 20% 必须先 A 再 B，结果直接调 B
    📁 路径错误 15% 文件不存在、权限不够、相对路径 vs 绝对路径
    ⏱️ 超时错误 10% 命令执行太慢、网络超时、死循环
    🔑 权限错误 5% Token 过期、没登录、API Key 不对
    📊 格式解析错误 5% 期望 JSON 结果返回了 HTML、编码问题
    ❓ 文档与实际不一致 5% 官方文档写的和实际接口不一样

    真实踩坑案例：

    ❌ 2026-07-28：skill_view(name="xxx.md") 报错 原因：参数 name 不需要 .md 后缀，文档没写清楚 后果：浪费 10 分钟排查问题

    ❌ 2026-07-27：git commit 失败 原因：之前没 git add，直接就 commit 了 后果：多花 5 分钟重试

    2. 五层防御体系架构¶

    第 5 层 🧠 学习层：从失败中提取规则，加入知识库
  ↑
第 4 层 📋 校验层：调用前自动过检查清单，不符合就不调用
  ↑
第 3 层 🚨 告警层：出错了快速定位，附常见原因和解决方案
  ↑
第 2 层 🔄 重试层：瞬时错误自动重试，指数退避
  ↑
第 1 层 📝 观测层：记录所有调用，成功失败都留日志

    每层的职责¶

    层级 作用 目标
    L1 观测层 所有调用全记录，参数 + 耗时 + 结果全存 出问题能复盘，能统计失败率
    L2 重试层 网络波动、瞬时错误自动重试 90% 的临时问题不需要人管
    L3 告警层 出错了给足信息，附排障清单 排查时间从 10 分钟 → 1 分钟
    L4 校验层 调用前检查参数、前置依赖 把错误拦在调用之前
    L5 学习层 每次失败都沉淀成规则 同样的坑永远不踩第二次

    3. 错误分类与根因分析¶

    3.1 参数错误（占 40%）¶

    典型模式：

    - 参数名拼写错误：skill_view(name="...") vs skill_view(file="...")
- 格式错误：路径带/不带后缀、日期格式不对
- 类型错误：传了字符串但要数字
- 多余参数：传了不需要的参数
- 缺必选参数：漏了必填项

    防御措施：

    ✅ 调用前对照文档核对参数名
✅ 每个工具建立「正确调用示例」卡片
✅ 不确定时先看参数定义，不要瞎猜

    3.2 顺序错误（占 20%）¶

    典型依赖链：

    git 操作：修改文件 → add → commit → push
Docker 操作：build → run → exec → stop → rm
文件操作：mkdir → cd → 写文件 → 读文件
API 操作：登录 → 获取 Token → 调用接口

    防御措施：

    ✅ 每个有顺序的工具建立「调用链」图
✅ 调用 B 之前自动检查 A 有没有成功
✅ 第一次用某个工具先看完整的示例流程

    3.3 路径错误（占 15%）¶

    典型坑：

    - 相对路径 vs 绝对路径
- 当前工作目录不是你以为的那个
- Windows vs Unix 路径分隔符
- 文件存在但没读权限
- 父目录不存在，写文件失败

    防御措施：

    ✅ 永远用绝对路径，不用相对路径
✅ 操作文件前先检查文件是否存在
✅ 用 pathlib 处理路径，不要手动拼字符串
✅ 检查父目录是否存在，不存在就先创建

    3.4 超时与性能错误（占 10%）¶

    典型模式：

    - 网络请求默认超时太长（或者根本没设）
- 大文件操作没进度反馈，不知道卡在哪
- 递归/循环没设终止条件，死循环了

    防御措施：

    ✅ 所有网络请求设合理超时（10-30 秒）
✅ 大操作加进度条或定期日志
✅ 循环设最大次数保护
✅ 超过预期时间自动终止并告警

    3.5 权限与认证错误（占 5%）¶

    典型模式：

    - API Key 过期了自己不知道
- 环境变量没加载成功
- 登录态失效了
- 对某个文件/目录没权限

    防御措施：

    ✅ 启动时先检查所有需要的 Key/Token
✅ 权限问题作为单独的失败分类
✅ 认证失败自动触发重新登录流程

    4. 已知工具坑知识库¶

    Hermes 内置工具¶

    ✅ skill_view¶

    ❌ 踩坑记录：
  2026-07-28：传了带 .md 后缀的 name 参数报错

✅ 正确用法：
  skill_view(name="tool-call-bootstrapping")
  注意：name 参数只传技能名，不要 .md 后缀

✅ 校验规则：
  - 如果 name 里包含 .md → 告警提示去掉后缀
  - 先调用 skills_list() 确认技能存在

    ✅ terminal¶

    ❌ 常见坑：
  1. cd 只影响当前命令，下次就失效了
  2. 相对路径和你想的不一样
  3. Windows vs Unix 命令差异

✅ 正确用法：
  # 不要：
  terminal(command="cd xxx && do-something")

  # 要：
  terminal(command="do-something", workdir="/absolute/path/to/xxx")

✅ 校验规则：
  - 检测到 command 里有 cd → 提示改用 workdir 参数
  - 路径用绝对路径，不用相对路径

    ✅ read_file / write_file¶

    ✅ 校验规则：
  - 写文件前检查父目录是否存在
  - 读文件前检查文件是否存在
  - 大文件 (>1MB) 提示考虑分块读取
  - 写文件前提示文件会被完全覆盖，确认是想要的行为

    ✅ web_search¶

    ✅ 校验规则：
  - 中文问题尽量用中文搜索
  - 技术问题用英文搜索更准确
  - 加年份过滤过时内容
  - 结果超过 5 条提示只看前 3 条高质量的

    5. 工具调用检查清单¶

    ✅ 调用前必过的 5 个问题¶

    1. 📝 参数对吗？
   ▢ 参数名拼对了吗？
   ▢ 有没有漏必选参数？
   ▢ 参数格式对吗（要不要后缀、要不要前缀）？
   ▢ 有没有传多余的参数？

2. 🔄 前置条件满足吗？
   ▢ 需要先调用别的工具吗？
   ▢ 需要的文件/目录存在吗？
   ▢ 需要登录/认证吗？Token 有效吗？

3. 📁 路径对吗？
   ▢ 用的是绝对路径吗？
   ▢ 路径分隔符是跨平台的吗？
   ▢ 父目录存在吗？
   ▢ 有权限读写吗？

4. ⏱️ 超时设置合理吗？
   ▢ 有没有设超时？
   ▢ 超时时间够吗（网络 30s，大文件 5min）？
   ▢ 超时了有重试机制吗？

5. ❓ 失败了怎么办？
   ▢ 这个操作幂等吗？失败了能重试吗？
   ▢ 失败了会有副作用吗（文件删了/覆盖了）？
   ▢ 有没有回滚方案？

    6. 失败复盘模板¶

    每次工具调用失败，用这个模板复盘，把经验沉淀下来：

    ### 工具调用失败复盘：[工具名]

#### 发生时间
YYYY-MM-DD HH:MM

#### 现象描述
（怎么出错的，报错信息是什么）

#### 期望行为 vs 实际行为
期望：xxx
实际：xxx

#### 根因分析
1. 直接原因：（为什么出错了）
2. 根本原因：（为什么会犯这个错，为什么没防住）

#### 解决过程
（怎么修好的，花了多久，试了哪些方法）

#### 提取的通用规则
（把这次的教训变成以后能用的规则，越具体越好）
✅ 规则 1：xxx
✅ 规则 2：xxx

#### 改进措施
- [ ] 把规则加入本工具的校验层
- [ ] 更新本 Skill 文档
- [ ] 有没有办法在 L4 校验层就拦住？
- [ ] 有没有办法加自动化检测？

#### 复盘结论
本次踩坑花费时间：XX 分钟
同类错误以后能不能避免：✅ 能 / ⚠️ 部分能 / ❌ 不能

    7. 自举闭环工作流¶

    步骤 1：工具调用失败 / 告警
    ↓
步骤 2：自动分类（参数 / 顺序 / 路径 / 超时 / 权限）
    ↓
步骤 3：查找已知坑知识库，有没有记录过？
    ├─ ✅ 有记录 → 直接给出解决方案
    └─ ❌ 新坑 → 进入复盘流程
    ↓
步骤 4：用「失败复盘模板」完整记录
    ↓
步骤 5：提取通用规则，加入对应层级
    ├─ L4 校验层：加入调用前检查
    ├─ L3 告警层：加入失败提示
    └─ L5 知识库：加入本 Skill
    ↓
步骤 6：下次调用同类工具时，自动应用规则
    ↓
✅ 同样的坑，永远不踩第二次！

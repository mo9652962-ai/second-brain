    墨题账单/支付管理——功能性与安全性千轮深研（2026-08-23）¶

    触发：sora 指定课题「墨题账单管理问题的功能性和安全性」 背景：墨题（英语刷题机）已有 v9.32 AI 每日配额（EPM_AI_DAILY_QUOTA）+ 用量记录；未来要做付费/订阅/账单功能 方法：IterResearch 式——5 个子问题覆盖率清单 + 12 信源交叉验证 数据截止：2026-08-23

    覆盖率清单¶

    # 子问题 状态
    1 支付回调的安全铁律（验签/幂等/乱序）？ ✅
    2 订单状态机与数据模型怎么设计？ ✅

    🎯 结论置顶¶

    账单系统的第一性原理：资金状态以渠道为准，业务状态以本地为准，两者通过可信回调+幂等更新+补偿任务保持最终一致。 安全侧的四大铁律：服务端验签、金额服务端校验、条件更新幂等、异常落库不丢弃。

    墨题现状评估：v9.32 的每日配额是「用量记录」不是「计费系统」——真要收费，以下设计清单直接可用。

    一、支付回调安全铁律（最高优先级）¶

    微信支付 V3 验签要点（官方文档实证）¶

    1. 原始报文体验签：签名是对字节序列计算的——任何框架的 JSON 中间件先解析 body 都会导致验签必败。Express 的 express.json() 是经典事故源；只在回调路由挂 raw-body parser
    2. 构造验签名串三行：时间戳\n + 随机串\n + 报文主体\n，用微信支付公钥 SHA256-RSA 验证
    3. 探测流量：微信会极少数故意发错误签名探测商户是否严格验签——不特殊处理，按正常验证（带 WECHATPAY/SIGNTEST/ 前缀可事后排查）
    4. CDN 可能过滤 Wechatpay-* 头 → 回调地址直连不走代理

    支付宝异步通知五重校验（官方文档）¶

    验签通过后必须再校验： 1. out_trade_no 是本系统创建的订单号 2. total_amount 等于订单创建时的实际金额 3. seller_id 匹配该订单操作方 4. app_id 是自己的 5. 任一不过 = 异常通知，忽略

    回调处理七步流水线（OSCHINA 教育系统方案实证）¶

    验签 → 解析 → 查订单存在 → 幂等检查(已支付直接返回成功)
→ 金额校验(不一致=告警) → 条件更新(原子推进状态) → 写本地消息表(同事务)

    关键纪律： - 回调假设自己会被重复调用、乱序调用（支付宝 25 小时内重发 8 次：4m/10m/10m/1h/2h/6h/15h） - 已支付订单收到重复回调 → 返回成功（让渠道停止重试），不做任何写 - 金额不一致 → 返回失败 + 高等级告警，绝不静默 - Stripe 生态同理：raw body 验签 + event.id 唯一约束去重 + 2xx 快速返回 + 重活异步

    二、订单状态机与数据模型¶

    订单表必备字段（教育系统实证 schema）¶

    CREATE TABLE order_info (
  order_no VARCHAR(32) UNIQUE,        -- 业务订单号全局唯一
  user_id BIGINT,
  goods_type/goods_id,                 -- 商品快照
  goods_name, original_amount, pay_amount,  -- ⚠️ 金额快照：商品改价不影响历史订单
  status TINYINT,                      -- 0待支付 1已支付 2已关闭 3已退款
  trade_no,                            -- 渠道流水号（对账/追踪）
  expire_time,                         -- 超时关单依据
  INDEX idx_expire_status (expire_time, status),
  INDEX idx_user_status (user_id, status)
);

    状态机合法流转表¶

    当前 目标 触发 允许
    待支付 已支付 渠道成功回调且验签通过 ✅
    待支付 已关闭 超时且渠道确认未支付 ✅
    已支付 已退款 退款成功回调 ✅
    已退款 已支付 重复/乱序回调 ❌

    代码层保留状态机校验，但高并发下真正推进状态靠数据库条件更新：

    UPDATE order_info SET status=1, trade_no=?, pay_time=NOW()
WHERE order_no=? AND status=0 AND pay_amount=?;
-- 更新 0 行 = 已被处理过 = 幂等返回成功

    进阶模式（orderd 开源项目 DESIGN.md）¶

    • payment_attempts 分表：处理「结果未知」窗口（下单冻结账号/金额/渠道快照）
    • payment_transactions 不可变流水表：UNIQUE(channel, account, transaction_id)——重复回调命中唯一键后重读原流水全量比对
    • 异常资金不丢弃：第二笔真实付款/金额不符的真实交易 → 仍插入 anomaly=1 流水并提交告警，不回滚丢证据
    • idempotency_key + request_hash（确定性序列化后 SHA-256，长度前缀序列化消除字段边界歧义）

    下单环节三细节¶

    1. 前端传入金额不能作为入库依据（一分钱充五块的严重漏洞就是这么来的——edu 小程序真实案例：抓包改 totalfee 参数）
    2. 待支付订单复用必须带 goods_type（避免课程 ID 和考试 ID 撞号）
    3. 关单前先查渠道状态（用户刚付款但回调未到的窗口期）

    三、对账兜底（生产必备后台任务）¶

    任务 频率 逻辑
    超时关单 每 5 分钟 expire_time 过期 + 待支付 → 先查渠道状态再关单
    主动查单 递进间隔 5s/30s/1m/3m/5m/10m/30m 轮询未确定订单；10 次未支付则关单
    日账单对账 T+1 日上午 拉渠道 T 日账单逐笔核对：正常 / 商户侧未标支付(补发货或退款) / 单号找不到(排查数据异常)
    滚动对账 日切场景 23:59:59 支付 00:00:02 回调跨天 → 前日异常数据去次日找匹配
    消息补偿 持续 本地消息表重试超限 → 人工队列

    微信官方建议的对账四分类：匹配且都成功=正常；匹配但商户侧非成功=决定补发或退款；账单有单号本地没有=排查数据异常；本地成功但账单没有=排查 bug。

    四、AI 配额计费：并发扣减防超卖¶

    这是墨题最相关的部分（v9.32 配额系统升级路径）：

    Redis 两阶段扣减（掘金 LLM 多租户实践）¶

    # 请求前：预扣（input + max_output 保守估算）
pipe.incrby(daily_key, estimated_tokens)
pipe.expireat(daily_key, next_day_ts)

# 请求后：结算退还多预扣
delta = estimated - actual_tokens
redis.decrby(daily_key, delta)

    quota-meter 开源项目的 Lua 原子化（关键设计）¶

    TOCTOU 竞态：GET 和 INCRBY 之间另一个实例读到同样的旧值 → 双双超扣。 解法：幂等检查 + 配额扣减放进单个 Lua 脚本（Redis 执行 Lua 原子，无命令可穿插）： 1. 查 idempotency key 是否存在 → 有则返回缓存结果 2. 读 limit 和 usage 3. remaining ≥ requested → 扣减并写请求记录 4. 否则写拒绝记录

    配套决策： - 全有或全无（60 余额拒 100 请求，不部分满足） - 退款的钱绑定原请求记录（不能由调用方任意指定退款额——防超额退款） - 月度 key 自然过期自转（quota:{org}:{feature}:{YYYY-MM} TTL 35 天），无 reset 竞态 - Redis 不可达时 fail closed（503）而非 fail open - 三层配额：租户日额度 / 功能日额度 / 用户档位日额度

    告警三级¶

    级别 阈值 行为
    L1 预警 70% 通知不限流
    L2 告警 90% 软降级（降并发）
    L3 熔断 100% 写熔断标志，后续请求不再查计数直接 429

    五、客户端 VIP 判定攻防边界¶

    攻击面清单（博客园实战视角）¶

    攻击 手段 防线
    本地存储篡改 改 SharedPreferences/SQLite 标记字段 本地 isVip() 只是状态快照，权威在服务端
    函数 Hook Hook isVip() 永远 true 关键动作服务端鉴权；多点校验
    网络重放 替换响应包 时间戳+nonce+请求体签名
    变种包 改包名重打包 关键逻辑校验官方签名

    架构原则（一句话版）¶

    VIP 状态 = 服务端权威 + 本地缓存 + 多维度校验

    • 低风险动作（UI 美化/去广告）：可用缓存状态
    • 高价值动作（导出/精讲 AI 调用）：服务端每次鉴权——checkUserPermission(userId, action) 查 status/expireTime/planType 多维度
    • Google Play 补充：purchaseToken 全局唯一做主键（不要用 orderId！促销码购买没有 orderId）；后端 consume/acknowledge；Voided Purchases API 收回已退款权益

    真实漏洞案例警示（edu 小程序）¶

    一分钱充值五块钱电费的完整链路：垂直越权（roleid 4→6 进教师端）→ 抓包发现金额校验包 → 修改支付 API 调用包的 totalfee 参数 → 一分钱到账任意金额。根因：金额校验在前端/校验包完成，支付包本身不校验。教训：金额必须在服务端从订单快照读取，任何客户端传来的金额只是参考。

    六、墨题落地建议（优先级排序）¶

    优先级 动作 依赖
    P0 现有配额系统加固：扣减改 Lua/事务原子操作，加「预扣-结算」两阶段 无（现有 SQLite 可用条件更新实现）
    P0 所有金额比较用 DECIMAL 快照比对，不信任何客户端传值 无
    P1 若接微信支付：回调路由独立 raw-body + V3 平台证书验签 + 七步流水线 商户号
    P1 订单表按上述 schema 建，含 expire_time + idx_expire_status P1 支付
    P2 定时任务族：超时关单/主动查单/T+1 对账（Hermes cron 天然适合跑） 订单表
    P2 权益开通走本地消息表（订单更新与权益发放同事务解耦） P1
    P3 客户端 VIP 缓存 + 高价值动作二次鉴权 服务端权限体系

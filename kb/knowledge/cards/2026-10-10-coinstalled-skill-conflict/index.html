    🃏 知识卡片 · 技能装多了会互相抢跑：五次运行被抢走一次，而 99.1% 的回复不告诉你是谁干的¶

    来源：arXiv 10-10 速览（10-05 ~ 10-09 全新窗口，34 主 + 48 简评）· 官方源：arxiv.org abs 页（2610.11647 / 2610.04832 摘要已由 k 于 2026-10-10 curl 直连逐句核对） 一句话：技能装到 459 个之后，真正的问题不是「技能有没有害」，而是两个干同一件事的技能同时存在时，跑的是哪一个——冲突在「第一次读技能」那一刻就定了，任务照样通过，所以只看完成率的测试永远看不见。

    核心洞察 / 影响¶

    维度 内容
    ① 冲突有多常见 One Skill Too Many（2610.11647）：从 20,947 个仓库快照挖出 822,109 个疑似相似技能对，LLM 判定 3,754 个分层样本，在 3 个模型上跑 312 个确认对（6,368 次运行 / 169,294 次工具调用 / 542 agent 小时）。结论：近 1/4 的已装技能都有一个「做同一件事」的共存者，37% 被判定技能位于拷贝合集里
    ② 怎么坏的 不降低任务完成率的前提下，相似技能在五次运行里抢走一次；先打开相似技能的那次运行，丢掉超过 1/3「只有原技能才提供」的独占核心功能——比如「禁止碰 git」这类硬约束被绕过，而任务仍然「通过」
    ③ 谁在决定 安装位置决定谁跑，列表顺序几乎无关；冲突在首次技能读取时即已决定（几乎总在改动任何文件之前）。在那一处加一个 pre-tool hook，能把独占核心功能还原到「先打开已装技能」的水平
    ④ 最刺眼的数字 最终回复只在 0.9% 的替换运行里点名实际使用的技能——也就是说 99.1% 的情况下，你看不出这次到底是谁干的活
    ⑤ 改技能怎么才有用 Agent Skill Evolution（2610.04832，3,159 技能 / 2,608 对首末修订）：55% 的修订改了某条规则或流程；新增一条规则平均把单次回答遵从度提高 +0.41、4 个 agent 的「采取所需动作」率 +0.23（+0.16~+0.36）、盲审正确率 +0.10。增益主要来自「点名了旧技能没提到的命令或路径」的规则——泛泛描述几乎无效
    ⑥ 成本也要算 一次修订给单次回答增加 18–19% 输入 token，对 agent episode 无可测成本；但加载技能正文平均让 episode token +50% → 正文要精简，硬规则放最前

    关键数据 / 对 sora 与 k 的影响¶

    1. 🔴 本地实测（本次 cron 当场扫描，非引用）：Hermes 活跃技能 459 个 SKILL.md（已排除 .archive），其中同名重复 2 组——ai-image-generation（@okaris 版 4.5KB vs 自建版 16.6KB）、manim-video（creative/ 版 vs video-use/skills/ 版）；按 description 词袋 Jaccard ≥0.5 判定的近似对 5 组（claude-code‖codex 0.60、export‖transcription 0.56、export‖verification 0.55、transcription‖verification 0.53、remotion-render‖remotion-studio 0.50）。同名重复是真风险（触发条件完全一致、只有加载顺序能决定谁跑），近似对不同功能（codex/claude-code 是两个不同的 CLI）属误报，需人工复核
    2. ⚠️ 「任务过了」不等于「技能生效了」：本文的核心方法论警告——评估技能不能只看任务完成度，要专测独占核心功能（如「不许碰 git」「必须先备份」「敏感词必扫」）。k 的 skill-audit 目前只看 description 是否过时，没有独占功能断言
    3. 💡 技能正文加载有 50% token 成本：这解释了为什么「把规则塞满 SKILL.md」是负收益——正确做法是正文只留点名具体命令/路径的硬规则，长尾内容挪到 references/
    4. ✅ 交付/回复里点名实际生效的技能：现状只有 0.9%，是巨大且低成本的改进空间——k 报「我用 X 技能做的」就能把这条差距抹平

    行动项¶

    • [ ] 处理 2 组同名技能：ai-image-generation（保留自建版，把 @okaris 版改名或归档）、manim-video（二选一，另一份归档）——同名 = 触发条件完全重叠，是最高优先级的冲突源
    • [ ] 给 3~5 个高风险技能各写一条独占核心功能断言（「不许碰 git」「发布前必须过隐私门禁」「图片敏感词必扫」），纳入 skill-audit 周期测试
    • [ ] 技能修订按本文配方：新增规则点名具体命令/路径（这是 +0.41 的唯一来源），正文保持精简
    • [ ] 交付回复里点名本次实际生效的技能（现状 0.9%）

    为什么重要¶

    • 补上 k 自己的技能安全链最后一环：10-02 卡片讲「装的时候危险」（技能即供应链，25.1% 走通危险路径）→ 10-04 卡片讲「执行的时候危险」（批准的动作 ≠ 执行的动作）→ 今天这张讲「共存的时候危险」（多个技能抢跑、不报名字）。三张合起来，技能生命周期才闭环
    • 直击 sora 的工作方式：sora 的偏好是「全都要」——搜索/模型/技能一次配多个冗余。冗余在模型侧是容灾，在技能侧是冲突：同一件事有两个技能，谁跑由安装位置决定，而输出不会告诉你。这条对「全都要」原则是一个精确的边界修正
    • 内容选题：「你装了 200 个技能，其中四分之一有人在跟它抢活，而 99% 的回复不告诉你是谁干的」——有出处、有反直觉数字、有本地实测，是能讲清的工程向选题

    Go 逆向能力升级：从「函数名」到「源码行号」¶

    结论置顶¶

    能力 升级前 升级后
    函数名 + 地址 ✅ 1956 条 ✅ 1956 条
    源码文件清单 ❌ ✅ 226 个（calc.exe）/ 959 个（mnemon.exe）
    源码行号定位 ❌ ✅ 1798 条（calc.exe）/ 13642 条（mnemon.exe）
    Ghidra 注释内源码位置 ❌ ✅ 1639 个函数
    与 GoReSym 交叉验证 ❌ ✅ 函数数完全一致（15774）

    一、搜索引擎研究：GoReSym 是业界标准¶

    研究 mandiant/GoReSym（FireEye/Mandiant 出品，Go 逆向事实标准）：

    项 内容
    pclntab 支持 ≥ Go 1.2，布局覆盖 pre-1.2 / 1.2 / 1.16 / 1.18 / 1.20
    特性 stripped 二进制、UPX 畸形、跨段拆分数据、moduledata 定位、magic 被篡改后修复
    输出 UserFunctions / StdFunctions / Types / Interfaces / Files / Strings
    集成 IDAPython / GhidraPython / BinjaPython 三套重命名脚本

    关键洞察：GoReSym 的 Files 字段来自 pclntab 的 filetab —— 而这正是我们 debug/gosym 已经能拿到的数据（tab.Files + tab.PCToLine），只是之前没输出。

    二、实测：GoReSym 装上了，但对 calc.exe 失效¶

    go install github.com/mandiant/GoReSym@latest   # v1.7.1 装成
GoReSym.exe -d -p -t D:/tools/targets/calc.exe
# {"error": "Failed to parse file: failed to read pclntab: failed to locate pclntab"}

    强制版本 -v 1.20 / 1.22 / 1.24 全部同样报错。

    根因（实测字节级）：

    Go1.18 magic @ 0xddf68  minLC=1 ptrSize=8

    calc.exe 的 pclntab 用 Go 1.18 magic（0xfffffff1），但 GoReSym 对 PE 的扫描逻辑在此样本上没命中。而我们的 gosymtab 能正确解析（因为它扫 4 种 magic 并做结构校验）。

    但 GoReSym 对 mnemon.exe 正常 —— 说明这是 GoReSym 的样本兼容性局限，不是我们的问题。

    三、交叉验证：我们的解析器准确¶

    工具 mnemon.exe 函数总数
    GoReSym 15774（7009 user + 8765 std）
    gosymtab 15774

    完全一致。 这证明 pclntab 解析实现正确，可以放心用于生产。

    四、新能力 1：源码文件清单（-files）¶

    gosymtab.exe -files D:/tools/targets/calc.exe
# 源码文件数: 226
# <autogenerated>
# D:/tools/go/go/src/cmp/cmp.go
# D:/tools/go/go/src/errors/errors.go
# ...

    mnemon.exe → 959 个源文件，含完整 GOPATH 路径（C:/Users/USERNAME/go/pkg/mod/github.com/spf13/pflag@v1.0.9/bool.go）。

    情报价值：从二进制直接读出依赖版本（pflag@v1.0.9）、模块路径、甚至原作者本地构建路径。

    五、新能力 2：源码行号定位（-srcline）¶

    gosymtab.exe -srcline D:/tools/targets/calc.exe "main."
# 0x140047880  runtime.main.func2  D:/tools/go/go/src/runtime/proc.go:207
# 0x140071ea0  runtime.main.func1  D:/tools/go/go/src/runtime/proc.go:174
# 0x1400a6260  main.main           D:/tools/targets/calc.go:18

    覆盖率实测：15771 / 15774 个函数有源码定位（99.98%），只有 3 个 <autogenerated> 汇编桩无定位。

    六、新能力 3：源码位置写进 Ghidra 注释¶

    ApplyGoSymbols.java 升级支持三列格式解析，把 Source: file:line 写进 plate comment。

    实测 calc.exe：

    DUMPCOMMENTS: total=1757 with_comment=1754 with_source=1639

    Ghidra 里打开任一函数，注释区直接显示：

    1400a6260  main.main  ||  Source: D:/tools/targets/calc.go:18
140001080  internal_abi.BoundsDecode  ||  Go symbol (original): internal/abi.BoundsDecode | Source: D:/tools/go/go/src/internal/abi/bounds.go:86

    1639 / 1757 = 93.3% 的函数带源码定位（其余是无 filetab 的汇编桩）。

    七、大型二进制压测：mnemon.exe（4.98MB）¶

    bash apply-go-symbols.sh "C:/Users/USERNAME/go/bin/mnemon.exe" mnemon_gosym
    指标 值
    符号数 15774
    源码文件 959
    带源码定位 13642（86.5%）
    Ghidra 已命名函数 14002 / 14010（99.94%）
    failed 0
    耗时 5 分 21 秒

    注意：mnemon.exe 未 strip，Ghidra 自带符号表已认出 13781 个，我们额外补了 221 个（含被 Ghidra 漏掉的）。skipped_existing=13781 是正常的。

    对比 calc.exe（strip 过的）：1757 函数全是 FUN_xxx，我们补了 1754 个 —— 这才是本工具的主战场。

    八、三个新增能力的实现要点¶

    8.1 标志位解析要支持任意顺序¶

    for len(args) > 0 {
    switch args[0] {
    case "-json":    jsonOut = true
    case "-srcline": showSrc = true
    case "-files":   showFiles = true
    default:         goto flagsDone
    }
    args = args[1:]
}

    8.2 默认输出格式必须保持不变¶

    -srcline 是可选的，默认仍是两列 address name —— 因为 ApplyGoSymbols.java 依赖这个格式。加了三列后 Java 侧必须能同时解析两种格式：

    int sp2 = rest.indexOf("  ");
if (sp2 > 0) {
    String maybeLoc = rest.substring(sp2).trim();
    // 只把形如 X.go:123 的尾巴当源码定位，避免误切含空格的 Go 泛型名
    if (maybeLoc.matches(".*\\.(go|s|c|h|cc|cpp):\\d+$")) {
        rawName = rest.substring(0, sp2).trim();
        srcLoc = maybeLoc;
    }
}

    坑：Go 泛型名含空格（HashTrieMap[go.shape.interface {},...]），不能用空格简单切分，必须用 ".go:数字" 正则锚定。

    8.3 debug/gosym 的 PCToLine 是核心¶

    if file, line, _ := tab.PCToLine(fn.Entry); file != "" && line > 0 {
    row.File = file
    row.Line = line
}

    tab.Files 是 map[string]*Obj，遍历 key 得文件清单。

    npm run check  →  10 sh + 4 java → syntax OK
npm test       →  24 + 62 = 86 条断言，0 失败

    两项反向验证均生效：

    注入破坏 期望 实际

    Java 里 Source: 改成 X: 测试失败 FAIL Source 注释，61/1 ✅
    恢复 全绿 62/0 ✅

    十、能力边界（观察 / 推断 / 未知）¶

    观察： - gosymtab 对 mnemon.exe 输出 15774，与 GoReSym 完全一致 - calc.exe 的 pclntab magic 是 0xfffffff1（Go 1.18 布局），即使 Go 版本是 1.26.6 - 源码定位覆盖 15771/15774（99.98%） - GoReSym 对 calc.exe 报 failed to locate pclntab，对 mnemon.exe 正常

    推断： - GoReSym 的 PE pclntab 扫描在 calc.exe 这个特定布局上失效（可能是段边界或 magic 位置特殊）；我们扫 4 种 magic + 结构校验，容错更好 - pclntab 布局版本 ≠ Go 运行时版本（Go 1.26.6 仍用 1.18 布局），这是 GoReSym README 明确说明的设计

    未知： - GoReSym 的 Types / Interfaces 对 mnemon.exe 返回 0 —— 未查清是解析失败还是该二进制真无 typelinks（-t 已传） - 未验证 GoReSym 的 garble（符号混淆）检测能力

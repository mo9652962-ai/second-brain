    墨题（英语刷题机）安全自审报告¶

    目标：D:\english-multiple-choice-practice-machine（FastAPI 后端，自家产品） 时间：2026-08-22 | 方法：src-bug-hunting 防守审计清单（上线前安全自审） 状态：✅ v9.30 四洞修复（11/11 冒烟）+ v9.30b 全路由扫描（22/22 冒烟 + 17/17 临时验证），两轮共 13 文件修复，已推送 GitHub 结论：单用户/局域网模式安全（默认）✅；多人模式（EPM_AUTH=1）全路由 user_id 隔离完成 🔧

    一、漏洞清单（多人部署场景）—— 修复状态¶

    🔴 [HIGH-1] AI 对话跨用户访问/删除（IDOR）—— ✅ 已修复¶

    项 内容
    位置 routers/ai.py:101（GET 对话）/ :556（DELETE 对话）/ :542（chat）
    问题 SELECT * FROM ai_conversations WHERE id = ? / DELETE ... WHERE id = ? —— 无 user_id 过滤 + 路由未挂认证依赖
    攻击链 用户 A 枚举 GET /api/ai/conversations/1..N → 读到用户 B 全部 AI 对话（作文批改/精讲/口语记录）；DELETE 可删任意用户对话；POST /api/ai/chat 可接管他人对话续聊（消耗 AI 额度）
    修复 ① 路由挂 Depends(require_user) ② 查询加 AND user_id = ?（当前用户）③ chat 校验 conversation 归属

    🔴 [HIGH-2] 业务数据无用户隔离（错题/练习/作文全共享）—— ✅ 已修复¶

    项 内容
    位置 routers/wrong.py（0 认证依赖）/ practice / essays / speaking / review（全部 0 依赖）
    问题 查询按全局活跃 profile_id（get_active_profile_id）而非 user_id；wrong_stats 表有 user_id 字段但查询未用
    攻击链 任意登录用户 GET /api/wrong → 看到所有用户的错题/练习记录/作文（用户学习数据泄露）
    修复 查询统一加 AND user_id = ?（未登录时用 IS NULL 兼容单用户）；路由挂 maybe_require_user

    🟡 [MEDIUM-3] 首用户注册劫持管理员 —— ✅ 已修复¶

    项 内容
    位置 routers/auth.py:126 is_first = COUNT(*) == 0
    问题 空库时第一个注册用户自动成为 admin——部署者未抢先注册则被攻击者抢注
    修复 ① 部署时初始化管理员（seed 脚本/环境变量 EPM_ADMIN_USERNAME）② 或首个注册限时窗口+邀请码

    🟡 [MEDIUM-4] 登录接口无限流（暴力破解面）—— ✅ 已修复¶

    项 内容
    位置 security_middleware.py:37 PUBLIC_PATHS 含 /api/auth/login
    问题 PUBLIC_PATHS 完全跳过中间件（含限流） → 攻击者无限尝试口令（PBKDF2 慢但可持续）
    修复 login 增加独立限流（按用户名/IP 失败计数，5 次/15 分钟锁 15 分钟）

    二、安全项验证通过 ✅¶

    检查点 结果
    API Key 存储 ✅ DPAPI（CryptProtectData）加密，不落明文
    密码存储 ✅ PBKDF2-HMAC-SHA256 100k 迭代 + 随机盐
    会话 token ✅ secrets.token_urlsafe(32) opaque token，服务端查表
    字符串比较 ✅ hmac.compare_digest 常量时间
    XFF 防伪造 ✅ 仅 EPM_TRUST_PROXY 显式配置才信任
    CORS ✅ 白名单仅 localhost:5173
    管理接口 ✅ AI settings/profiles 有 _require_admin_when_enabled
    部分业务隔离 ✅ vocabulary/exam 路由有 user_id 过滤（6 处依赖）
    SQL 注入面 ✅ 全部参数化查询（? 占位）
    启动备份 ✅ SQLite online backup + 保留 5 份
    导出清理 ✅ exports/ 24h 自动清理

    三、修复优先级建议（上线多人模式前必修）¶

    P0（阻塞发布）: HIGH-1 AI 对话隔离 + HIGH-2 业务数据隔离
  → 两处都是「认证框架已有但业务路由漏挂」——加依赖 + WHERE user_id
P1（尽快）: MEDIUM-3 管理员初始化（seed 或环境变量）
P2（加固）: MEDIUM-4 登录限流（失败计数锁）

    四、经验沉淀¶

    🔑 核心教训: 「认证框架存在 ≠ 路由被保护」
  墨题有完整的 auth 体系（PBKDF2/token/依赖函数），但 29 个路由里
  ai/essays/speaking/wrong/review 5 个路由组漏挂依赖 = 认证形同虚设
审计方法: 统计每个路由文件的 require_user 挂载数 vs @router 数
  → 0 依赖的路由文件 = 重点审计对象（大概率有洞）

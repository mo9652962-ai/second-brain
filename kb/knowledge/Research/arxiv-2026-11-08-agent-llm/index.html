    一、评测与可靠性：数字到底在测什么（5 篇）¶

    1. XStack: A Benchmark for ML Repo Migration¶

    • ID: 2611.08472v1 | 📄 PDF
    • 作者: Linrong Cai, Taiming Lu, Haozhe Chen, Zhuang Liu
    • 分类: cs.LG / cs.AI | 提交: 2026-11-05
    • 摘要: ML 代码应该跑在研究者选择的地方，而不是它最初被写下的地方。今天 ML 代码基本只活在两个生态里：PyTorch + NVIDIA GPU、JAX + Google TPU。跨这两个生态迁移仓库意味着跨框架、跨硬件地构建与测试。作者把「迁移」本身做成基准：agent 收到一个 PyTorch 仓库和一台干净的 TPU 机器，必须交出一个 JAX 仓库，判分依据是源仓库已发表的结果（由作者认证并校准）。结果很不乐观：Claude Opus 5 通过率 75%，GPT-5.6-sol 45%，其余所有 agent 不超过 40%。
    • 关联度: ★★★★ 这是「整仓多文件一致性」任务的标准形态，和 sora 让 Codex 改墨题后端、迁移依赖是一类问题。可落地：验收锚点用原仓库已发布的结果（测试/指标），而不是「能跑起来」；迁移类任务先要一份可执行的对拍基线。

    2. Hard Issue, Weak Model, or Bad Run? Rethinking Failure Prediction for Coding Agents¶

    • ID: 2611.08285v1 | 📄 PDF
    • 作者: Xingyue Shi, Wesley K. G. Assunção
    • 分类: cs.SE | 提交: 2026-11-05
    • 摘要: 轨迹式失败预测器读 agent 的部分轨迹，判断这次 run 是在往对的方向走还是走歪了，走歪就中止、重试或换模型。作者问：这些预测器真的学到了「这次 run」吗？在 SWE-bench Verified 上（每个模型对每个 issue 只跑一次），两个与 run 无关的因素主导了预测器表现：① issue 难度——一个完全不看 run、只看「这题对别的模型有多难」的参考分就能到 AUROC 0.92，而轨迹预测器只有 0.62；② 模型能力——同一 issue 内，知道是哪个模型跑的，比预测器本身还准。除掉难度和能力之后，轨迹带来的增益统计上等于零。这个混淆也污染了下游动作：换模型的理论收益来自「最好单模型 vs 任意模型 oracle」的差距，而这个差距不超过随机波动；按 issue 换模型在留出集上零收益。重复跑实验里，同一个模型对同一 issue 有时成有时败——重试确实有修复空间，但只救「坏 run」，救不了「超出能力」，而现有预测器分不清这两者。
    • 关联度: ★★★★★ 直接改写 k 的失败处理规则。现状是「3 连败即停」——方向对，但停完该做的是同模型重试 + 加预算，不是换模型。可落地：① 失败归因先分「题难 / 模型弱 / run 坏」，只有连续多次同模型失败才判定为「超出能力」；② 换模型只在能力档位明确不足时做，不做「按题切换」。

    3. Accepted but Wrong: Silent Failures of LLM Code Repairs after API Migrations¶

    • ID: 2611.08269v1 | 📄 PDF
    • 作者: Xiaobo Chen, Genliang Zhu, Ziyuan Wang, Chu Wang
    • 分类: cs.SE / cs.AI | 提交: 2026-11-05
    • 摘要: 运行时或 API 迁移之后，LLM 修好的函数能干净跑完却返回错误结果，而基于典型测试输入的发布检查会把它放出去。作者做了预注册研究：73 个任务、覆盖 CPython / 某数据库库 / SQLite 的 60 处有文档记录的变更，每个候选都在真实运行时上对着 withheld contracts 执行。全量修复空间上，典型输入的全断言门禁放过了 0.410 的错误修复；从 release note 里写出的一条边界输入把它压到 0.065（15 个未见簇上 0.061）；让一个没看过程序的盲写模型（GPT-5.6-luna）写三条输入，达到 0.070。继续加难：菜单扩到 1,491 个片段、再加 233 个在典型输入上与旧输出一致的硬干扰项后，边界输入仍有 0.168、前沿模型写手 0.153 的错误程序通过——说明难度可以无限逼近，但边际收益仍然可观。四个模型族里，边界输入在三套菜单、三个开放权重族上都降低了错发率（如 0.233→0.057），且不降低正确完成率。
    • 关联度: ★★★★★ 这就是 sora 刚踩的坑：pydantic ABI 错位（3.14 解释器调 cp311 扩展）——「装上了、导入了、没报错」，但语义是错的。可落地：任何迁移/依赖修复，验收必须加一条从 release note 抄来的边界输入（不是自己想的典型输入），这一条把漏放率降了 6 倍。

    4. Measuring the Marginal Value of Verifier-Based RL Beyond Supervised Fine-Tuning¶

    • ID: 2611.07639v1 | 📄 PDF
    • 作者: Amit Sagtani, Saloni Garg
    • 分类: cs.LG / cs.AI | 提交: 2026-11-05
    • 摘要: RLVR 通常被当成 SFT 的替代或后续阶段，隐含假设「RL 阶段自己有增益」。作者直接测这个增量：自建 gpu-train-debug，1,877 个合成 GPU / LLM 训练故障诊断任务、30 个原型，程序化 verifier 给部分分，难度校准到中档模型落在 0.60–0.75。试点就出意外：1,200 条 gold 示范几乎把基准解了（硬 split 上 SFT 0.785），而 15 步 GRPO 完全没动（0.314 vs 基线 0.311）。于是作者在正式跑之前书面修改研究问题：验证型 RL 在示范之外还能加什么？预注册规模（60 步 GRPO、lr=1e-6）的答案：分布内 +0.22 分，95% CI [−0.06, +0.51]，无可检测提升；分布漂移下 +0.33 分，CI [+0.02, +0.68]，小幅但可测。SFT 吃掉了大部分可得增益；SFT 残留的错误大多是系统性、跨样本一致的，这恰恰削弱了 GRPO 需要的组内信号。整个研究只花了 $8.69 算力，且可从归档生成物、冻结配置和带 tag 的代码完全复现。
    • 关联度: ★★★★ 对「微调就能提升」的期待降温：先看 SFT 天花板，再谈 RL。可落地：任何自训/微调实验先报三个数——SFT 后的分数、RL 后的分数、两者的 CI；只有 CI 不跨 0 才叫有效。

    5. ReproBridge: Building Reproducibility into ML Research Artifacts¶

    • ID: 2611.08452v1 | 📄 PDF
    • 作者: Yubo Wang, Rui Meng, Jaehyun Nam, Tomas Pfister, Jinsung Yoon
    • 分类: cs.AI | 提交: 2026-11-05
    • 摘要: 复现 ML 实验要从论文、发布代码、辅助工件里拼出过程。对编码 agent 来说，复现成功往往取决于它们能不能补齐缺失细节，而不只是工件本身。作者定义一套标准工件设计——精修代码库、环境安装、实验启动器、复现指南——并提出 ReproBridge 这个构建工件的工作流。ReproBridge-Bench 含 1,029 个任务、387 个实验、36 篇论文，每个任务配 5 个人工核验的参考分；独立 Auditor 检查执行证据。四个模型上，精修工件把平均复现成功率从 76.4% 提到 92.6%，下游 API 花费平均降 19.7%，跨模型成功率差距从 21.6pp 收窄到 3.9pp（四个模型全部 >90%）。消融显示任何组件拿掉都掉分，其中代码与环境影响最大。
    • 关联度: ★★★★★ 这条最省钱：提升不来自更强模型，来自把执行知识写下来。可落地：sora 的交付包（论文服务/数模/PCB）统一四件套——精修代码 + 环境脚本 + 一键启动 + 复现指南，验收时用 Auditor 式检查（不是「我跑过了」而是留下执行证据）。

    6. Cognitive Tours: Making Understanding a Deliverable in AI-Assisted Development¶

    • ID: 2611.08456v1 | 📄 PDF
    • 作者: Margaret-Anne Storey
    • 分类: cs.SE | 提交: 2026-11-05
    • 摘要: Agentic coding 在加速开发，也带来技术债之外的两种更不显眼的债：认知债（团队共享理解缺失，没人能自信解释系统怎么运作、改动会波及什么）和意图债（目标、约束、理由没有被清晰表达，系统「为什么这样」无从追溯）。作者提出 Cognitive Tours：一个 web 原型，让人创建并沿「curated path」走——路径串起用户需求、设计决策、代码、测试、开放问题；AI 技能负责审计已有 waypoint 与 tour 是否过时、是否有问题、并建议新增候选，人负责决定什么重要、验证关系、构建叙事。这种分工是刻意保留「productive friction」：挑选、解释、修订 tour 的过程本身就是理解的形成与传递。

    7. ReConMem: A Graph-Based Dual Memory System for Repository-Oriented Conversations¶

    • ID: 2611.07759v1 | 📄 PDF
    • 作者: Zhishuo Yang, Li Zhang, Yang Liu, Donghao Yang, Fang Liu
    • 分类: cs.SE | 提交: 2026-11-05
    • 摘要: 仓库级迭代开发里，助手必须同时用上演化中的对话历史和仓库上下文。现有记忆系统是为通用对话设计的，没有把对话信息和它指向的代码实体协调起来。ReConMem 提出图式双记忆：把蒸馏后的对话记忆与对话相关代码实体组织成语义图 + 结构图，并随交互演化维护跨图关联；召回时用代码草稿做查询落地（code-draft-based query grounding）把自然语言和代码对齐，再沿图内/图间关系扩展，并按结构粒度压缩检索到的代码。LoCoEval 上 Pass@1 比最强基线高 7.917 / 7.292 个百分点（单跳 / 多跳），上下文压缩程度相当；CodeAssistBench 上 27.61% Correct / 44.03% Partially Correct，比「全量历史」高 4.10 / 7.09 个百分点，交互质量也更好。
    • 关联度: ★★★★ 记忆要挂在代码实体上，而不是纯文本块。可落地：给墨题项目建一份「实体记忆」——文件/函数/表名 ↔ 相关决策与踩坑，用代码片段当检索键，而不是靠自然语言回忆。

    8. SKIM: Pruning Large Language Model Agents via Selective Knowledge Informed Masking¶

    • ID: 2611.07558v1 | 📄 PDF
    • 作者: Moonseok Choi, Jongwon Jeong, Minki Kang, Giung Nam, Juho Lee
    • 分类: cs.CL / cs.AI | 提交: 2026-11-05
    • 摘要: Agent 越来越多在结构化生成（grammar 约束输出格式）下部署，而现有压缩方法都针对无约束生成。作者先指出一个根本错配：结构化生成把输出分布压到合法 token 上，logits 只在少数决定 agent 动作的位置才真正重要。据此提出 SKIM——首个面向结构化生成下 LLM agent 的剪枝 + 蒸馏框架，两个阶段都由 token 角色引导：把位置分成 context / decision / format 三类，① 类别感知的剪枝显著性分数，优先保住对 decision 位置最相关的参数；② on-policy 蒸馏，让学生在合法 token 上对齐教师，并配类别感知的特征匹配。在工具调用基准和多步 agent 循环上、跨多个模型规模与稀疏度，SKIM 都稳定优于基线，高稀疏率下优势最明显（传统方法在此崩得最厉害）。
    • 关联度: ★★★ 与「本地小模型跑 tool-calling」直接相关（4060 8GB 的现实约束）。可落地：将来做本地 agent 压缩时，评估指标要盯 decision 位置的准确率，不是整体困惑度。

    • ID: 2611.07510v1 | 📄 PDF
    • 作者: Zhenlong Dai, Zhuoluo Zhao, Xiu Tang, Sai Wu, Chang Yao, Zhipeng Gao, Jingyuan Chen
    • 分类: cs.CL | 提交: 2026-11-05
    • 摘要: 仓库级补全的难点在于从仓库里挑对上下文和跨文件依赖推理。作者提出一个 RL 框架，三个部件：① identifier-driven intent recognition——用标识符捕捉补全意图，改善文件内与跨文件上下文理解；② reward-driven completion learning——在复杂仓库场景里对补全结果给奖励；③ selective-exploration——把探索集中在低置信、高回报的 token 上，促使模型探索有价值但少见的补全模式。实验显示相对 Code LLM 基线有显著提升，代码与数据集已公开。

    三、记忆与长程上下文（2 篇）¶

    10. MEMOIR: A Training-Free Memory Lifecycle for Long-Horizon LLM Agents¶

    • ID: 2611.07631v1 | 📄 PDF
    • 作者: Mayank Anand, Subham Raj, Aman Vaibhav Jha, Sriparna Saha
    • 分类: cs.IR | 提交: 2026-11-05
    • 摘要: 长程 agent 需要跨会话保留有用信息并在需要时取回。现有系统把「写」和「取」当成两个独立问题：记忆在写入时就打了静态重要性分，用完之后永不修订。这产生两个耦合的失效模式——压缩会静默销毁未来查询需要的证据，而检索会持续偏向已经过时的记忆。MEMOIR 提出一个免训练的记忆生命周期：压缩前用筛查门测试「与答案相关的证据是否被保留」，每次查询后用归因估计哪些被检索的记忆支撑了答案，并据此更新它们的检索优先级；再加一个 UCB 式探索奖励，鼓励取回曝光不足的记忆，避免高频记忆挤掉有用但少见的证据。在 1,905 条去重 LoCoMo QA 上，完整检索栈把 evidence recall@5 提升 11.92 个百分点（对比裸余弦），confidence-gated 反馈在无参考答案、无 reranker 训练的前提下再加 1.50 分；judge-gated merge 让文本证据召回从 58.82% 到 59.08%，活跃库减小 1.42%，100 次独立审计合并 0 次损失（单边 95% 上界 2.95%）。在线写路径不需要额外 LLM 调用，merge 筛查放在周期性离线整合里。
    • 关联度: ★★★★★ 这就是 mnemon 的失效风险说明书：现在的 consolidation 只看「重不重要」，不看「以后还会不会用到」。可落地：① 记忆条目加「上次被哪次回答用上」的归因字段；② 压缩/合并前跑一次保留筛查（拿最近 20 个真实问题回测，看证据是否还在）；③ 保留 UCB 式探索，别让高频记忆垄断召回。

    11. SMART: State-based Multi Agent Reasoning Traces for Verification-oriented Problem-Solving¶

    • ID: 2611.08196v1 | 📄 PDF

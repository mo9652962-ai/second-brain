    联合工作千轮研究升级 v1.5 — 2026-08-31¶

    流程：k 拆题 → 4 方向摸底搜索（编排框架/通信协议/MCP生态/可观测性）→ 3 子代理并行深挖（搜索成功、汇总撞 429，按"一次核实即证伪"不重派，k 用自身摸底+子代理 URL 完成核验）→ 技能 v1.5 落地。 技能：multi-agent-research v1.4 → v1.5

    一、研究方法与执行¶

    • k 摸底：4 方向并行搜索，覆盖 LangGraph/CrewAI/MAF/OpenAI SDK/ADK、MCP+A2A、AACP/AAHP/G2CP、AGENTTRACE/TraceElephant
    • 子代理派发：3 个 leaf 并行（编排框架/通信协议/可观测性），密任务包 8 槽
    • 子代理结果：搜索全部成功（Magentic-One PDF / MAF 1.0 / CA-MCP / AACP / AAHP / AGENTTRACE / TraceElephant 等关键源已抓到），汇总阶段撞 RPM 429（fallback 对 delegation 子代理的 RPM 级限流未生效）
    • 处置：不重派（同一 provider RPM 未恢复，重跑大概率再 429）——k 用自身摸底完整结果 + 子代理 URL 交叉核验，完成沉淀

    二、核心研究结论（三方交叉）¶

    1. 编排框架收敛（2026 Q3）¶

    框架 抽象 状态 关键点
    LangGraph 状态图+checkpoint 生产级 可恢复、可审计、HITL interrupt
    CrewAI 角色制 crew 快速原型 token 开销最大（角色+目标+背景每次注入）
    Microsoft Agent Framework 1.0 5 模式统一 2026-04 GA AutoGen 继任者；Magentic-One + MCP 原生 + A2A coming
    OpenAI Agents SDK 显式 handoff MCP-first handoff=工具调用，透明
    Google ADK 生产运行时 Vertex 生态 层级编排
    • Magentic-One 关键机制：Manager(Planner) + Task Ledger（任务台账：状态/依赖/结果，透明可重规划）+ 动态重派
    • CA-MCP（arXiv 2601.11595）：中央 LLM 只做高层规划，MCP 服务器经 Shared Context Store 自主协调 → 执行快 73.5%、makespan 短 45.5%
    • 成本铁律：每轮循环重发累积历史 → 成本随步数平方增长；简单任务单 agent 优先（64% 任务匹配或超越多 agent）

    2. 通信协议（密任务包升级依据）¶

    协议 核心 节省 适用
    Routed Graph Handoff (2608.25277) 轻量 router 选图/NL 图压缩 2-3× 依赖链任务才用图，AppWorld 回归 -14.6pp → 保守默认 NL
    AACP 确定性 pipe 包 59 hops 零 LLM 协调调用，省 18-85% 已知工作流模板化
    AAHP MANIFEST.json 分层读取 87% token 文件型交接
    G2CP 图操作通信 73% token 需知识图（构建 200-500h）
    payload-by-reference 传引用不传数据 3KB → 61 token（22.9×） 大材料交接（已落地 v1.5①）

    3. 可观测性与故障归因¶

    • AGENTTRACE（2603.14688）：因果图回溯，sub-second，69× 快于 LLM 分析；LLM 基线 47.4% 归因错误 = 选了表现点而非根因
    • TraceElephant（ACL2026）：全执行可观测性 → 归因精度 +76%；缺输入会漏 21% 失败原因
    • llmmas-otel：OTel 追踪 + 故障注入（重工具，小团队不采用，但"可注入故障测试边界"思路值得留）

    三、v1.5 已落地增强（4 条）¶

    1. 密任务包 payload-by-reference：大材料传引用不传全文（22.9× token 节省）；prior findings 仍原样贴
    2. Task Ledger 任务台账：派发时建 1 行状态台账（pending/running/done/failed + 依赖 + 结果）→ 失败可见可重规划
    3. 根因回溯核验：子代理失败先问三连（最早哪步偏离/任务书有无歧义/输入完整吗），不直接归因子代理
    4. 长链成本意识：重试 >2 次降级（换源→拆小→单 agent 串行）；长链只传必要中间态

    四、过程教训（新）¶

    • delegation 子代理也会撞 RPM 429（本次 3/3 全撞）——fallback 链对子代理的 RPM 级限流不生效（fallback 主要兜 TPM）。大规模并行派发前先确认 RPM 窗口，或错峰/限并发
    • 子代理搜索成功但汇总失败时：live transcript 里的 URL/搜索结果是有价值中间产物，可直接取用（本次就靠它完成了核验）
    • 千轮研究不必每次都开满多 agent：k 摸底 + 子代理补充 + 自身核验的组合，在限流环境下反而更稳

    采纳的新方向（3 条，已入 v1.6）¶

    1. Agent 记忆四层（工作/情景/语义/程序）——压缩正交维度，失败诊断存"调试记忆"复用
    2. HILA 过程级人机协作——任务书标注 checkpoint、拆段派发、Task Ledger 显式依赖
    3. 窄域专业化——每个 agent 只做一件事（WorkBuddy 只调研/dsh 只数据/Codex 只编码），工具越多故障越多

    铁律强化（本次实证）¶

    • 跨源盲评价值实证：WorkBuddy 给的修正/新方向中 5/7 有效，是"同源只确认风格"的对照物

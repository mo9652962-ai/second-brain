    1. Silent Failures in Agentic Security Evaluation: A Validated Harness for Tool-Call Mediation Under Indirect Prompt Injection¶

    • ID: 2609.32691v1 | 📄 PDF
    • 作者: Animesh Shaw
    • 分类: cs.CR, cs.LG
    • 摘要: 调用特权工具的 LLM agent 面临间接提示注入（IPI），但评测本身的有效性几乎无人审查。作者审计了一个 IPI 基准及其 harness，识别出四类缺陷：静默 payload 未投递、按工具身份而非参数判攻击成功、把误拒率与模型能力不足混为一谈、缺少审计轨迹——每一类都能产出一个「看起来合理、可发表、但错误」的数字。用同一批真实执行轨迹按缺陷定义与修正定义分别重打分：工具身份评分器报 21.7% 攻击成功率，而真实参数级成功率只有 1.2%；最刺眼的案例中，某开源模型此前报告 62.8%，在修正 harness 下变成 0%——原数字主要是 payload 未投递 + 身份级评分造成的假象。作者放出修正 harness，使每类缺陷「不可表达」：机器可校验的 payload 放置、参数级攻击谓词、逐场景环境、强制轨迹持久化；并借此报告领域内缺失的三个量：被攻陷 agent 是否自曝、LLM-judge 防御的完整安全/效用曲线、工具调用能力与过度拦截的解耦。修正 harness 还推翻了一个已发表的「能力壁垒」：被判无工具使用能力的模型其实完全有能力，早先结论是环境不匹配的产物。
    • 关联度: ★★★★★ 这是本份最该抄的一篇：它把「评测 harness 本身会静默产假数字」拆成四类可机检缺陷，而 k 的 verify 脚本与 cron 校验正是同类 harness。可落地：① 给 k 的门禁加「参数级而非存在性」判据（不是「有没有调用」，而是「调用参数是否符合契约」）；② 把「静默未投递」当独立失败模式——断言必须先证明输入真的到达被测环节；③ 任何防御/拦截类指标必须同时报「能力/效用曲线」，否则无法区分「拦住了」与「根本不会做」。与既有 tool-call-bootstrapping、hermes-codex-security-gate 直接合流。

    2. API Secrets Should Never Become Tokens in the LLM's Vocabulary: A Threat Analysis of API Credential Handling in LLM Agent Systems and an Empirical Evaluation of a Vault-Mediated Execution Boundary¶

    • ID: 2609.33371v1 | 📄 PDF
    • 作者: Patrick Kenney, Hadi Ahmadi, Denis Lusson, Donald Nguyen, Gurbinder Gill
    • 分类: cs.CR, cs.AI, cs.LG
    • 摘要: 工具型 LLM agent 把凭据卫生从「存储问题」变成「执行安全问题」：一旦 key 被粘进 prompt、写进 system prompt 或工具配置，它就从认证边界跨进了数据管线，可能残留在对话历史、日志、记忆库、生成代码与错误负载中；提示注入与过度自主再把被动泄露升级成未授权动作。本文形式化 agentic 系统的凭据暴露威胁链，综合平台密钥库事故、厂商密钥蔓延测量、OWASP/NIST 指引，并给出vault 中介执行架构：模型只选连接器标识符，由受信请求边界提供认证。对生产实现 Corvic Security Vault 做两组受控黑盒实验：7 个控制域 16 个探针全部符合预期——GitHub API 请求成功，而凭据在进程环境变量、调用方可见请求头、被测文件系统位置、三个第三方回显服务、两个无关 API 源中均不存在，两个云实例元数据端点均不可达。同时报告一个负面结果：某连接器的 header 映射不满足其 provider 的认证契约——集中托管本身不保证配置正确。结论：vault 中介消除若干泄露路径，但必要而非充分，最小权限、确定性动作授权、人工审批、遥测脱敏、轮换仍各自独立必需。
    • 关联度: ★★★★★ 直击 k 的现实：apikey-manager 桌面 vault（DPAPI）、custom_providers 配置、多个反代与中转站 key——key 一旦进 prompt/日志就等于进了数据管线。可落地：① 排查 k 的所有 cron/脚本，凡把 key 值（而非标识符）写进 prompt、命令行或日志的，改成「连接器标识符 + 受信边界注入」；② 给日志/报告加一道凭据脱敏扫描（正则 + 高熵串检测），并把它列为交付前门禁；③ 记住本文的负面结论——集中托管 ≠ 配置正确，vault 本身也要有验证探针。

    3. Trust the Brand, Lose Control: How Identity Hijacks LLM Agent Orchestration¶

    • ID: 2609.32635v1 | 📄 PDF
    • 作者: Xutao Mao, Rui Qian, Linghan Chen, Yudong Gao, Junchi Liao, Jiulin Cai, Jinman Zhao, Cong Wang
    • 分类: cs.CR, cs.AI
    • 摘要: LLM agent 已能端到端执行任务并编排能力与成本各异的子 agent。以往工作把子 agent 选择当优化问题，但编排器是依据子 agent 展示的身份做选择的，而攻击者可以伪造身份。于是「展示的身份」实际决定了操作权限——谁被信任去复核工作、谁被允许改动系统。结果是：即使其他证据与之矛盾，有风险的子 agent 仍能保住执行权。作者提出 TrustFork：1,890 个任务、27,826 条有效轨迹、16 个 agent 系统（8 个编排器 × OpenCode/OpenClaw/Pi 三种 harness）。每个任务里一个子 agent 携带风险目标、另三个与用户对齐，因此矛盾证据可能存在；任务还可在不更换底层模型的前提下改变子 agent 展示的身份，从而把权限转移归因到标签本身。结论：即使另一个子 agent 提出反驳，编排器平均仍有 72.0% 的情况下照风险回答执行；交换家族标签使编排器获得风险回答的频率接近三倍；84.0% 的任务本存在更安全的回答，但只有 25.0% 的决定采用了它。三种运行时防御中，隐藏身份线索最稳定有效，而「执行前验证」只在 harness 返回足够证据时才起作用。
    • 关联度: ★★★★★ k 的日常就是多模型编排（Codex / WorkBuddy 反代 / dsh / Gemini / K3 试点按任务类型分工）。本文说明：按「品牌/型号标签」路由而不按证据路由，会把权限交给一个只是自称可靠的执行者。可落地：① 委派任务时把「谁复核」绑定到证据而非模型名（例如 Codex 的产出必须由独立通道验证，不因它是 Codex 就免检）；② 尝试「隐藏身份线索」这条最有效的防御——让评审/复核环节看不到产出是谁写的，只看内容；③ 与 ai-api-provider-evaluation（中转站注水）合流：注水检测看能力，本文看权限归属。

    4. Share-Borne AI Virus: Memory-Hopping Attacks Across LLM Agents¶

    • ID: 2609.35576v1 | 📄 PDF
    • 作者: Sidharth Pulipaka, Ansh Sharma, Stanislau Hlebik, Leonidas Raghav, Vyas Raina, Ivaxi Sheth, Mario Fritz
    • 分类: cs.AI, cs.CL, cs.CR, cs.LG
    • 摘要: LLM 越来越多被部署为跨交互保留信息、并用工具读写持久产物的有状态助手。当这些产物在用户之间共享时，它们就构成了本来彼此独立的助手之间的间接通信信道。本文研究这一信道支撑的自传播攻击：提出 artifact-mediated propagation（产物中介传播）——通过某个产物（如一份报告）引入的对抗内容，被存进助手的持久记忆、在随后创建的产物中复现、再被后来读到它的另一个助手获取。作者在模拟独立助手之间产物交换的时序人-agent 宇宙中评测：攻击能否存活连续多次交接、能跳几跳、扩散多广。结果：攻击可跨多个独立助手传播并在长交互序列中持续；在更大规模模拟环境中，即使 GPT-5.6 Luna 也出现显著扩散，触达 60–80% 的 agent，传播链最长 8 跳。说明持久产物能充当对抗状态的耐久载体，使攻击比单次交互活得更久、并跨越隔离的助手传播。
    • 关联度: ★★★★★ 对 k 是结构性命中：k 的知识库本身就是一个「产物中介信道」——速览笔记 → 知识卡片 → MOC → 下一天的速览都读它；而 cron 之间也在互相读彼此的产出（09-26 实测 knowledge-card cron 会读当日速览抽卡片）。一旦某篇被污染，就会顺着这条链传下去。可落地：① 给 cron 产物加来源标注（谁写的、读自哪、可信度），让下游能区分「我验证过的」与「我读来的」；② 把「读来的内容」与「自己验证的内容」在笔记里显式分区（本文的传播正是靠无法区分二者）；③ 与第 13 篇（共享记忆的认知准入）合起来看——记忆写入是攻击面，不只是功能。

    5. AgentBoundary: Counterfactual Evaluation of Safety in Tool-Using LLM Agents¶

    • ID: 2609.33658v1 | 📄 PDF
    • 作者: Tianzhuo Yang, Zirui Mi, Yantao Huang, Guoxi Zhang, Jiawei Chen, Yaodong Yang, Jingwei Yi
    • 分类: cs.AI
    • 摘要: 对话场景的安全对齐围绕「回答还是拒绝」，但 agentic 场景下同一模型必须在执行过程中、随权限相关证据浮现来决定「是否行动」。这带来一个独特难题：表面风险、动作许可性、任务能力三者极易混淆，使得 agentic 过度拒绝无法与普通任务失败区分。作者提出 AgentBound，首个面向工具型 agent 安全的四路反事实生成与评测框架：对同一可执行工作流独立变化「表面风险」与「动作许可性」，从而受控比较「看着危险但已授权」与「看着常规但未授权」的任务，在控制任务能力的前提下同时诊断过度拒绝与不安全服从。实例化为人工校验的 4,000 任务评测套件，含轨迹级与后状态级判定。17 个模型×harness 配置的结果：高安全常与授权任务完成率低并存——GPT-5.5 拦下 99.5% 的「常规外观但未授权」动作，却只完成 28.7% 的「风险外观但已授权」任务。作者进一步训练轻量运行时校准模块，在 10 个配置上平均提升授权任务完成率 18.2%、同时提升不安全动作拦截 5.4%。
    • 关联度: ★★★★★ 这条直接给 k 的「审批层」提供了正确的问题形状：安全不是「拦得多」，而是「按权限证据行动」。可落地：① k 的自动化门禁/红线（凭据 BLOCKED、L3 授权）应做一次反事实自检——把同一个动作分别包装成「风险外观但已授权」和「常规外观但未授权」，看判定是否真的跟着许可性走而不是跟着措辞走；② 记录「过度拒绝」为独立指标（现在只记「拦住了」）；③ 与既有 Codex 红线（L0-2 自动 / L3 授权）对齐：表面风险 ≠ 不允许，否则会长期拖慢正常交付。

    6. Agent Safety From Within: Detecting Harmful Trajectories from LLM Internal States¶

    • ID: 2609.33039v1 | 📄 PDF
    • 作者: Difan Jiao, Ashton Anderson
    • 分类: cs.AI
    • 摘要: LLM agent 已能通过工具与 harness 执行复杂动作序列，能造成的损害范围随之扩大；而 guard 模型主要为内容审核设计，不适合检测这类 agentic 风险。作者先做表征分析再做方案：聚焦两类轨迹级 agentic 危害——直接表达的有害内容与依赖「动作是否与产生它的交互一致」的不安全工具使用。发现这两类危害在开源 guard 模型的内部表征中是线性可读的，尽管 guard 模型在「只差被调工具 schema」的成对样本上预测不优于随机；两类危害的内部方向几乎正交，彼此不可互相代理。据此提出 TACIT：对冻结骨干的内部状态做读出，不解码任何 token。在六个轨迹安全基准上训练，线性探针把平均 macro-F1 从最强开源 guard 的 62.3 提到 80.7，精炼读出达 86.2；逐基准完全留出训练时，精炼读出仍领先最强 guard（65.7 vs 61.1）。同骨干、同数据、同切分下，冻结读出与完整安全微调持平，且叠加在微调模型上还能进一步提升；探针训练参数量约为完整微调的百万分之一、时间约六分之一，延迟在所有被评 guard 中最低。
    • 关联度: ★★★★ 这条给 k 的交付前安全门禁指出一条低成本路线：不必再调一个 LLM judge 去读整条轨迹（贵、慢、还会被措辞骗），而可以在内部状态上做线性读出。可落地：① 对本地可跑的模型（llama.cpp/GGUF 线）试点内部状态探针，作为「轨迹级」安全检查的廉价通道；② 记住本文的关键实证——「只差工具 schema」的成对样本上 guard 不优于随机，这正是 k 的 verify 脚本最该补的负例形状（同一动作换接口表述）；③ 与第 5 篇合流：内容层安全与动作层安全是两条正交通道，不能互相替代。

    7. CoDeL: Co-Evolutionary Defense against Indirect Prompt Injection in LLM-based Agents¶

    • ID: 2609.34463v1 | 📄 PDF
    • 作者: Xiao Yang, Yangchen Ou, Yuhan Gao, Le Wang, Zonghao Ying, Aishan Liu
    • 分类: cs.CR, cs.AI
    • 摘要: LLM agent 依赖外部工具与内容，因此暴露于间接提示注入（IPI）；其中基于训练的防御常被认为最可靠。但现有训练式防御通常在静态的显式注入分布上优化，学到的是表面形式线索而非「服务用户 vs 服从注入目标」的边界，因此当恶意意图被折进一个可信工作流、并延迟若干轮才生效时就失效。作者提出 CoDeL：让防御者面对一个自己不断重塑的攻击分布。每轮用 LoRA 上的 GDPO、以安全/任务进展/格式合规的解耦奖励更新防御者，使「拒绝注入」与「完成用户任务」共同定义适应度；为持续供给值得学的失败样本，一个共演化的 prober 在注入轮次、攻击方法、payload 上搜索仍能穿透当前防御的注入，并同时以攻击成功率与攻击延迟为导向，优先挖掘「防御者发现得太晚」的突破。每次防御更新都会让部分攻击种群失效、迫使下一轮走向新前沿，把防御者自身的失败变成移动课程。三个 IPI 基准、九个基线、两个基座模型上：ASR 降低 88.5%，大幅领先其他基线（+38.0%）。
    • 关联度: ★★★★ 对 k 的启示不在训练侧而在红队方法侧：本文最有价值的机制是「按攻击延迟（latency）排序去挖漏网注入」——不是找最强的攻击，而是找最晚才被发现的攻击。可落地：① k 的注入/越权自检用例库按「被发现得有多晚」排序，优先补「延迟生效」类用例（跨轮、跨会话、藏在正常流程里）；② 静态用例集必然退化（本文的核心批判），用例库应随每次修复重新生成而不是冻结；③ 与 hermes-codex-security-gate 的 L 级策略合流——延迟型注入恰恰是「单轮判定」的盲区。

    4. 记忆既是攻击面也是治理对象，四条线各自给出机制：2609.35576（产物中介传播，GPT-5.6 Luna 也扩散到 60–80% agent、最长 8 跳）、2609.30813（假信念一旦无争议入库，消费者 0.97–0.99 照单断言；按来源类型门控把假采纳降到 0.06–0.09）、2609.33013（治理与质量是两个独立维度，r²=0.43；生产检索系统在跨层级迁移上得零分）、2609.30289/2609.32049（有效性感知检索、按承重定半衰期）。→ 转述不算验证；k 的知识库需要来源谱系 + 有效性维护 + 可逆/可审计。

    5. 路由与成本的正确形状：子任务级 + 规划期一次看全：2609.34712（RSI-router）在子任务级路由下以 48.3% 成本超过纯大模型基线，部分基准成本降 74.7–82.2% 而性能提升；2609.32917（PaR）在规划期一次看全整个工作流，相比全前沿路由省 44% 成本、让出 2.9 点。两篇都回避了「整会话切模型」——与 09-26 已收录的 2609.28919（切模型毁 prompt cache）合起来给出 k 重启智能路由的安全形状。
